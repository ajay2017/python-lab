What is deliberately NOT on this page
No gate, threshold, scoring weight or COMPOSITE_BUY. Why there is no "mark as refreshed" button
It would be a snooze button. If the date can move without the list changing, the amber becomes dismissible and the date stops being evidence and becomes a claim — strictly worse than today, where the date cannot lie because the only way to move it is to edit the file. as_of is stamped only on a real content change (hash comparison), never by a control you can press.

When the database is unavailable

Grow Today — scan universe unavailable

The scan universe could not be read from the database, so no new-position candidates are shown. This is not "no opportunities today" — the scan did not run.

⛔ Supabase RLS is blocking reads. The [supabase] key secret must be the service-role / secret key — not the publishable/anon key. Update SUPABASE_KEY in Railway → Variables, then Redeploy.
Why nothing is shown, rather than a fallback list.
This behaviour is already proven: during the 2026-07-24 Railway migration a wrong SUPABASE_KEY produced exactly this — no data, plus a message naming the cause and the fix. That is the safety net.

A silent fallback to a frozen code list would be the INTC failure mode: on 2026-07-14 load_all quietly served 5-day-old cached data, scored a name above the buy gate, and the app recommended a buy on stale inputs — fresh data scored the same name a Sell. An empty roster is also treated as unavailable, never as an empty universe, because "scanned nothing, found nothing" looks identical to a clean bill of health.

Open design questions this mockup does not answer

1. What does the cron do when the universe is unavailable? cron_runner.py imports SECTOR_UNIVERSE directly and must be moved onto the same resolver as the app. Single-source removes the divergence risk, but leaves one call: when the 9:45 ET morning-picks lane hits UNAVAILABLE, does it send nothing, or send an email saying the scan couldn't run? Recommend the latter — silence is indistinguishable from "no picks today", the same failure the empty-payload rule rejects.

2. Bucket renames. _DIVERSIFY_TO_DISCOVERY is keyed on both universes' bucket labels — renaming one here would silently degrade diversification suggestions. The UI must block a rename that orphans that map (a test catches it in CI, but a UI edit bypasses CI).

3. Replace vs merge. A save with 3 of 12 buckets populated is non-empty and would wholesale-replace the roster. Needs explicit semantics.

4. Editor ergonomics for ~200 tickers. The comma-separated per-bucket grid above is st.data_editor-shaped and buildable natively. A nicer chip UI would need interpolated HTML, which the repo's anti-pattern gate blocks for XSS reasons — so this grid is the honest, shippable version rather than the prettiest one.
