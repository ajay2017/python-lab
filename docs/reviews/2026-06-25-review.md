## High-Priority Issues

**[HIGH] ✅ RESOLVED (3622503) stock_analyzer/daily_briefing.py:1950 & 1970-1980 — risk-off TRIM can collide with an add-to-winner BUY on the same ticker**

- What is wrong: In build_daily_briefing, _buy_candidates is called at line 1950
  with act_today=act, but act does NOT yet contain the risk-off de-risk cards —
  those are computed at line 1970 (assess_risk_off_derisk) and appended to act at
  line 1976, AFTER _buy_candidates already ran. _buy_candidates builds its
  _act_blocked set from the pre-risk-off act, so a held high-beta Strong-Buy name
  that risk-off just flagged "TRIM 25%" can still appear in Buy Candidates as
  "ADD — Winning Position". _grow_today is safe (called at 1977 with the
  post-risk-off act); Buy Candidates is not.
- Why it matters: This is exactly the contradictory double-surface the calm-advisor
  posture (section 2B) and the single-surface rule exist to prevent — "trim AVGO 25%
  for risk-off" next to "add to AVGO". Acting on either is a real money move;
  surfacing both undermines trust in the decision.
- Suggested fix: Compute _risk_off and fold it into act BEFORE calling
  _buy_candidates (and _review_list), or pass the risk-off tickers into
  _buy_candidates exclusion set. Minimal change: move the _risk_off block
  (1958-1976) above the _buy_candidates call at 1950 so act is complete when every
  consumer reads it.

## Medium-Priority Issues

**[MED] ✅ RESOLVED (145c997) stock_analyzer/db.py:438 and 1057 — _json_safe is defined twice at module scope**

- What is wrong: Two top-level def _json_safe(obj) definitions. The second (1057)
  silently shadows the first (438). Both save_bundle_cache (484) and
  save_fundamentals_cache (1095) resolve to the line-1057 version at call time.
- Why it matters: Behavior is currently equivalent (both coerce NaN/inf->None, numpy
  scalars->native, recurse dict/list), so no live bug — but it is a latent trap: a
  future edit to the line-438 copy (which a reader naturally finds first, right above
  save_bundle_cache) would have ZERO effect, and a serialization regression there
  would be invisible. This is a documentation-integrity-grade hazard in a file whose
  cache writes already fail silently. Fact: py_compile does not flag redefinition.
- Suggested fix: Delete the line-438 definition, keep the line-1057 one (or vice
  versa); confirm both callers still resolve to the surviving copy.

**[MED] ✅ RESOLVED (7a35ac3) app.py:7316 — fundamental-score branch uses a hardcoded < 44 literal**

- What is wrong: if f_score < 44 chooses the "act with urgency" vs "technical-only
  weakness" prose for a review rebalance card. 44 equals COMPOSITE_HOLD but is
  applied to the FUNDAMENTAL leg and is a bare literal in app.py logic.
- Why it matters: It is branching logic, not pure cosmetics, and CLAUDE.md treats a
  literal like this as a defect. If the Hold floor moves in constants, this prose
  branch silently desyncs from the rest of the app.
- Suggested fix: Import and compare against a named constant (COMPOSITE_HOLD, or a
  dedicated FUNDAMENTAL_WEAK_FLOOR if the intent is distinct from the composite Hold
  floor — name the intent so the coupling is deliberate).

**[MED] ✅ RESOLVED (7b26106) stock_analyzer/scanner.py:95-104 — scanner signal-label boundaries are hardcoded (>= 80 / 65 / 45 / 30)**

- What is wrong: _quick_score assigns "Strong Buy / Buy / Hold / Weak / Avoid" labels
  off bare literals. 65 coincidentally equals COMPOSITE_BUY.
- Why it matters: These are momentum-scanner labels (Score is momentum-only, gated
  downstream by COMPOSITE_BUY), so NOT a policy-gate violation. But the coincidental
  65 invites a future reader to assume the scanner Buy label and the composite Buy gate
  are the same and "fix" one.
- Suggested fix: Either reference the constants (if alignment is intended) or add a
  one-line comment that these are an independent momentum scale, not the composite
  policy boundaries.

**[MED] ⏸ DEFERRED stock_analyzer/api_health.py:50-88 — record() mutates a shared module dict from worker threads (non-atomic increments)**

- What is wrong: _stats is a process-global dict; load_all fans out across
  DATA_LOAD_MAX_WORKERS threads, each calling record() which does s["calls"] += 1 etc.
  These read-modify-writes are not synchronized.
- Why it matters: Under CPython GIL the individual += 1 is effectively atomic, so
  counts are unlikely to corrupt in practice, but the circuit-breaker (in_cooldown,
  get_health red thresholds) reads several fields that interleaved threads can update —
  a transient miscount could trip or clear a cooldown a beat early/late. Impact is low
  (cooldown auto-recovers), but it is a genuine shared-mutable-state pattern.
- Suggested fix: If ever observed misbehaving, guard record() with a threading.Lock.
  Not urgent given concurrency is capped at 2.

**[MED] ✅ RESOLVED (2639e67) stock_analyzer/providers/orchestrator.py:263-264 — cross-check primary_name can mismatch the actual primary**

- What is wrong: crosscheck_price derives primary_name = order[0] from the configured
  order list, then skips that name to find an independent validator. But the real
  live-price primary used elsewhere is _live_price_providers()[0] — the first
  CONFIGURED+CAPABLE provider, not necessarily order[0] if order[0] is unconfigured.
- Why it matters: If the Finnhub key is absent, order[0] (finnhub) is still skipped as
  primary, so the loop could pick the wrong validator or skip a valid one — degrading
  the cross-check. The batch path (crosscheck_batch, 331-332) does this correctly with
  provs[0]/provs[1].
- Suggested fix: In crosscheck_price, set the primary from
  _live_price_providers()[0].name (mirroring crosscheck_batch) so single-ticker and
  batch paths agree on who the primary is.

## Patterns Worth Keeping

- Thresholds genuinely centralized. Every decision module imports from constants.py;
  the pure-logic modules (exit_advisor, decision_bucket, signal_reconciliation,
  position_lifecycle, signal_hysteresis, concentration) take primitives and are
  trivially unit-testable.
- One code path for app and cron. headless_alert_engine reuses bundle_loader,
  build_portfolio_df, deterioration_signals, and assess_risk_off_derisk — no
  re-implementation, so email alerts cannot disagree with the in-app Brief.
- None vs empty-container discipline. The offline-cache convention
  (_grow_today_sectors_cache = None on failure vs [] when computed-empty,
  app.py:2493-2506) is implemented as CLAUDE.md prescribes.
- Single-surface dedup is taken seriously. _consolidate_act_today, _reconcile_act
  (decision_bucket), and the news-WATCH final pass that re-derives the actioned set
  including action.trim_ticker (daily_briefing:1880-1894) show the recurring bug class
  is actively defended.
- NaN-Close defense in depth. compute_indicators and db.load_bundle_cache apply the
  SAME notna() filter (documented single source of truth), preventing the
  float(NaN)-is-truthy "$nan" class on both live and cached paths.
- ET-correctness everywhere. Every date boundary that matters (_today_et, FMP
  _next_earnings, market_status, cron gating, tax-lot dates) is
  America/New_York-localized with an explicit UTC-drift comment.
- Secret hygiene. FMPProvider._safe redacts the API key from error text before logging
  (the URL embeds ?apikey=), and send_email_resend never echoes the key or recipient
  on failure.

## Systemic Observations

1. Ordering coupling in the Brief builder is the live risk. The decision modules are
   individually correct; the one place a contradiction can still leak is when a
   producer (risk-off de-risk) is computed AFTER its consumers (Buy Candidates) have
   snapshotted the act list. The fix pattern is "compute every reduce signal, THEN
   build every consumer." The High finding is one instance; audit that all of
   _buy_candidates / _review_list / _grow_today see the SAME fully-assembled act.

2. app.py is 15.8k lines and carries decision-adjacent literals. Pure logic is
   correctly in stock_analyzer/, but display branches in app.py still hardcode boundary
   numbers that shadow policy constants. None are gates today, but the volume (a
   dozen-plus) erodes the "thresholds live in constants" invariant at the UI layer. A
   mechanical sweep into named constants during the UX pass would restore it.

3. Silent-cache-write swallowing is intentional but concentrated in db.py. The save_*
   cache functions swallow on failure by design; save_bundle_cache was already
   instrumented via api_health after a past invisible-failure incident. The duplicate
   _json_safe (Medium) is the one spot where this fail-silent philosophy could hide a
   real regression.

4. Provider seam is robust; cross-check has a minor primary-identity asymmetry. Batch
   and single-ticker cross-check derive who-is-primary differently (Medium finding).
   Unifying them removes a subtle correctness edge when the configured primary lacks a
   key.
