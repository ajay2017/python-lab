# DRISHTA — UX Audit
*2026-07-22 · full app · app.py (27,632 lines) + 68 reviewed `stock_analyzer/` modules (constants.py, db.py, data.py, bundle_loader.py, and pure-calculation files with no UI copy — indicators.py, scoring.py, sentiment.py, technicals.py, valuation.py, trades.py — excluded as out of scope)*

---

## Executive Summary

DRISHTA's action-clarity and edge-case handling are frequently excellent — the Trade Journal's SELL confirmation, the Analysis page's fundamentals-withheld verdict, and the suppression banners that explain *why* something was hidden (never silently filtered) all model the "decides, doesn't inform, but is honest about its limits" posture the app is built around. The single biggest opportunity is **consistency**: severity/tier vocabulary has fragmented into at least six unreconciled scales across modules (the in-app User Guide's own color-legend table implicitly admits this by having to translate five pages' worth of different words onto one 🔴/🟡/🟢 scale), several destructive delete actions apply the two-step confirm pattern inconsistently, and a handful of display strings hardcode a `constants.py` value as a literal rather than interpolating it — currently correct by coincidence, but silently driftable the next time a threshold changes.

## Critical Issues (fix before launch)

### C1 — Destructive delete/remove actions are inconsistently confirmed
- **Location**: Account cash-flow ledger delete ([app.py:21742-21744](app.py#L21742-L21744)); Watchlist sidebar bulk "Remove selected" ([app.py:15891-15899](app.py#L15891-L15899)); contrast with Watchlist per-card "REMOVE" ([app.py:16228-16247](app.py#L16228-L16247)) and Trade Journal's SELL/delete-trade flows, both of which use a two-step "Yes/Cancel" confirm.
- **Problem**: Verified directly. The Account page lets a user permanently delete a deposit/withdrawal history row with one click of a bare 🗑 button — no warning, no confirm, no undo copy — via `db.delete_account_flow()` firing immediately on click. The Watchlist page has **both behaviors for the identical action** (remove a ticker): the sidebar multiselect+button deletes on the first press, while the per-card "REMOVE" recommendation for the same ticker requires an explicit `st.warning("Remove **{ticker}** from watchlist?")` → Yes/Cancel step. A user who has learned "delete always asks me to confirm" from the Trade Journal or the per-card Watchlist flow can be caught off guard on the two unconfirmed paths.
- **Recommendation**: Apply the existing session-state-flag confirm pattern already implemented at [app.py:16229-16247](app.py#L16229-L16247) to both the Account cash-flow delete and the Watchlist sidebar bulk-remove button.

### C2 — Analysis page's "double-check before acting" evidence checklist hardcodes the single-name concentration threshold instead of importing it
- **Location**: [app.py:8106-8107](app.py#L8106-L8107) — `if act["weight"] > 15: _check("⚠️", f"Position is {act['weight']:.0f}% of portfolio — above 15% threshold...")`
- **Problem**: Verified directly. `SINGLE_NAME_CEILING = 15.0` is defined in `stock_analyzer/constants.py:56` for exactly this concept and is already imported into `app.py` and used correctly elsewhere. Here both the branch condition and the display copy use the bare literal `15`. CLAUDE.md's hard rule #1 states "Never hardcode decision thresholds... Changing a value there is an investment-policy decision." This check sits two lines above the section's own heading, "Evidence & Sources — Double-Check Before Acting" ([app.py:8112](app.py#L8112)) — the exact place a silently-stale threshold would undermine user trust most, since the value would visibly disagree with the real gate the rest of the app enforces the next time `SINGLE_NAME_CEILING` is revisited.
- **Recommendation**: Replace both occurrences of the literal `15` with `SINGLE_NAME_CEILING`.

### C3 — Severity/tier vocabulary has fragmented across at least six unreconciled scales
- **Location**: `stock_analyzer/risk_advisor.py` (HIGH/MEDIUM/OK, plus a one-off LOW at line ~564-577); `stock_analyzer/trade_review.py:1247` (`_SEVERITY_RANK`: critical/watch/good); `stock_analyzer/stress_test.py` `assess_fragility` (fragile/caution/calm); `stock_analyzer/watchlist_advisor.py:45-52` (HIGH/MONITOR/OK, introducing "MONITOR" nowhere else used); `stock_analyzer/exit_advisor.py` — **three separate vocabularies in one module**: WATCH/TRIM/EXIT tiers, Steady/Watchful/Defensive/"Risk-off & fragile" posture labels, and calm/caution/fragile fragility labels; `stock_analyzer/decision_quality.py:46-52` (Elite/Disciplined/Learning/Struggling/Critical); `stock_analyzer/macro_playbook.py` (PROTECT/WATCH/HOLD/OPPORTUNITY pre-event vs. ADD/HOLD/REDUCE/WATCH post-event, sharing only "HOLD"/"WATCH").
- **Problem**: The in-app User Guide itself ([app.py:23548-23571](app.py#L23548-L23571)) contains a severity-color legend table whose entire purpose is to reconcile the fact that Remove/Stop Breached/PROTECT/HIGH all mean the same 🔴 band on different pages — the drift is real and already documented as a known tradeoff, not a hypothesis. Some words are reused for genuinely different axes: "WATCH" means a portfolio-rebalance drift tolerance in `rebalancer.py` but a deterioration-signal tier in `exit_advisor.py`; "caution" is a directive *type* in `predictive_analytics.py` but a fragility *severity value* in `exit_advisor.py`. A user moving between Risk Advisor, Trade Review, Watchlist, and Exit Signals is decoding a new severity language on nearly every page, with only the User Guide's legend as a Rosetta Stone.
- **Recommendation**: Not a logic change — no gate, threshold, or scoring formula is touched, so this doesn't trigger the Opus-review hard rule. Scope a terminology-unification pass the same way the 2026-07-17 holding/pick/severity sweep was scoped, this time reaching module-internal tier vocabularies: reserve "WATCH" exclusively for the exit-signal tier; standardize risk-adjacent dashboards on one HIGH/MEDIUM/OK(/LOW) scale; stop reusing "caution"/"critical"/"danger" interchangeably for what the User Guide already treats as one three-band system.

### C4 — Leftover terminology from completed page/feature renames
- **Location**: `stock_analyzer/portfolio_health.py:258-261` — Health page's low-diversification improvement copy: `"Check the concentration section on Portfolio Allocation."` The page was renamed 🥧 **Portfolio Overview** on 2026-07-18 (confirmed current nav label at [app.py:1731](app.py#L1731): `("Overview", "🥧 Portfolio Overview", ...)`); "Portfolio Allocation" no longer exists anywhere in the nav. Separately, `app.py:21950` — Catalyst Watch's first tab is labeled `"📋 Positions"` ([app.py:21947](app.py#L21947)) but the markdown header rendered inside it still reads `"## 📊 Your Holdings — Earnings"`, a leftover from before the app-wide holding→position terminology sweep.
- **Problem**: Verified directly on both. A user following the Health page's own instruction to go find "Portfolio Allocation" will not find a page by that name — a dead pointer inside a feature whose entire job is to direct the user to the right next screen.
- **Recommendation**: Update `portfolio_health.py:260` to say "Portfolio Overview"; update `app.py:21950` to say "Your Positions — Earnings" (or drop "Your Holdings" entirely to match the tab's own "Positions" label). Add a grep-for-old-page-names step to CLAUDE.md's existing Definition-of-Done checklist for any future nav rename — this is exactly the class of drift item #3 in that checklist ("shipped queued item" staleness) already exists to catch, but for renames rather than roadmap items.

## Improvements (high value, not blocking)

### I1 — Several display strings hardcode a constants.py value as a literal instead of interpolating it
- **Location**: `stock_analyzer/portfolio.py:1040` (`"above the 20% sector cap"` — value matches `SECTOR_REDUCE_TRIGGER = 20.0` today, but isn't sourced from it); `stock_analyzer/macro_playbook.py:419` (`"Trim to ~15% weight"` — `target_w = SINGLE_NAME_CEILING` is computed one line above at line 414 but not used in the string); `stock_analyzer/recommendations_history.py:397-403,659-662` (composite-band labels "Strong Buy (≥75)"/"Buy (65–74)"/"Hold zone (44–64)"/"Sell zone (<44)" hardcoded in three places, matching `COMPOSITE_STRONG_BUY`/`COMPOSITE_BUY`/`COMPOSITE_HOLD` today); `stock_analyzer/risk_advisor.py` beta/Sharpe prose (literal 1.4/1.2/0.8/1.0 alongside gating logic that correctly uses `PORTFOLIO_BETA_CEILING`/`_ELEVATED`).
- **Problem**: All of these currently display the *correct* number — this is a drift-risk finding, not a live bug. But it's the identical bug class CLAUDE.md's own history documents being caught once already in Factor Tilt (`FACTOR_TILT_WINDOW_DAYS` existed but the fetch call hardcoded `period="6mo"` directly) — "a constant existing... doesn't mean the code actually reads it." Here the code *does* read the constant for gating, but the copy re-states the number independently, so the two can silently diverge the next time a threshold changes.
- **Recommendation**: Interpolate the constant into each f-string (e.g., `f"above the {SECTOR_REDUCE_TRIGGER:.0f}% sector cap"`) rather than restating its value.

### I2 — "Institutional Lens" prose density repeats a 5–6-paragraph card template across five modules
- **Location**: `stock_analyzer/rebalancer.py:201-208,281-288`; `stock_analyzer/risk_advisor.py:455-462,518-525,691-699`; `stock_analyzer/trade_analytics.py:281-288,342-349,471-478`; `stock_analyzer/watchlist_advisor.py:226-231,264-269,310-317,352-358,434-441,472-480`; `stock_analyzer/earnings_advisor.py:175-181,199-206,221-227,244-250,294-298`.
- **Problem**: Each card renders title/observation/implication/action/institutional-lens (5-6 text blocks). Individually well-written and good for building trust in *why*, but when several fire simultaneously (e.g., Risk Advisor showing 4-5 HIGH/MEDIUM recs in one session), the actual bolded directive risks getting buried in surrounding teaching-moment prose, and repeated exposure across pages risks pattern-blindness/banner fatigue.
- **Recommendation**: Keep the directive line bolded and first (already done in most cases); consider collapsing the "Institutional Lens" paragraph into a `st.expander("Why this matters")` so the scannable action stays above the fold and the teaching content is opt-in.

### I3 — "Today's P&L" metric label changes depending on data-tier availability
- **Location**: [app.py:4382,4400,4413](app.py#L4382) — the same Command Center metric slot renders as `"Today's P&L"`, `"P&L since {date}"`, or `"Today's P&L (held)"` depending on whether Tier B day-P&L data is available.
- **Problem**: A user comparing this metric day-over-day has no visual cue that the underlying scope (true day change vs. held-only mark vs. a multi-day catch-up figure) changed — the difference is only explained in a tooltip, not the label itself.
- **Recommendation**: Keep one stable label ("Today's P&L") and move the scope distinction into a fixed badge/tooltip icon next to it, rather than swapping the label text.

### I4 — The "Grow Today" panel is renamed per market tone, not just re-styled
- **Location**: `stock_analyzer/daily_briefing.py` (per [app.py:5380-5384](app.py#L5380-L5384)) — the panel title itself becomes `"📈 Grow Today"` (bull), `"🛡️ Defer New Entries"` (bear), or `"📈 High-Conviction Entries Only"` (flat).
- **Problem**: A daily user tracking "did Grow Today change since yesterday" may not immediately recognize these three headings as the same feature.
- **Recommendation**: Keep one stable panel title with a tone-dependent subtitle or colored badge, rather than three different headline strings for one panel.

### I5 — Developer/internal jargon leaks into a handful of user-facing strings
- **Location**: Recommendations History's "How to read this table" expander (~app.py:20515) says *"A Composite of NaN means..."* — raw programming term; the same page's empty state (~app.py:20064-20070) names the literal database table `recommendations`; Predictive Analytics' meta/audit expander (~app.py:21333) cites a doc file path (`docs/plans/next-evolution-strategy.md`) directly in copy; `stock_analyzer/fundamentals.py:246-249` names a specific data vendor ("Yahoo Finance") in a data-quality note, inconsistent with the app's otherwise vendor-agnostic framing; the sidebar Data Health expander ([app.py:1889-1944](app.py#L1889-L1944)) uses the unexplained abbreviation "RL" (rate-limit) alongside raw provider/table names.
- **Problem**: These are internal-audience artifacts (QA notes, schema names, vendor names) that made it into copy meant for the end investor.
- **Recommendation**: Replace "NaN" with "not yet loaded," drop the literal table name from the empty state (describe the condition in plain English instead), remove the file-path citation from the Predictive Analytics expander, and spell out "RL" (or replace with "Rate-limited: N").

### I6 — Predictive Analytics page mixes live analytics with what read as internal QA tooling
- **Location**: [app.py:21288-21497](app.py#L21288-L21497) — "Alpha Attribution — activates after 180 days" and "Behavioral Fingerprint — Data Readiness Audit" expanders sit below 5 live analytics tabs, and repeatedly show raw enum-like tokens (`buy_candidate`, `new_pick`, `add_winner`) in backticks rather than the friendly labels the page's own tables use elsewhere.
- **Problem**: These read as leftover internal audit artifacts (one of them, per the earlier `project_behavioral_fingerprint_audit` work, literally was a one-time Week-1 data-readiness check) embedded permanently in a user-facing page, with inconsistent label treatment vs. the rest of the page.
- **Recommendation**: Either promote these to full first-class sections with the same friendly-label treatment as the rest of the page, or move them to a lower-traffic surface (e.g., folded into the User Guide's "how the engine works" material) if they're primarily meant as one-time diagnostic context.

### I7 — AI Insights loads 8 metric tiles + 4 tabs before any tab content is visible
- **Location**: [app.py:23809-23932](app.py#L23809-L23932) — a 4-column "at a glance" status header, a second 4-column Behavioral KPI row, then 4 tabs.
- **Problem**: 8 distinct metrics render above the fold before the user has chosen a tab — exceeds the cognitive-load guideline for a single screen.
- **Recommendation**: Consider collapsing the Behavioral KPI row into the "🩺 Positions" tab it most relates to, leaving only the 4-tile "at a glance" strip always visible.

### I8 — Advisory-language tone is occasionally softer than the app's stated "decides, doesn't inform" posture
- **Location**: `"Best practice would recommend trimming..."` on 🌐 Macro (~app.py:13155) and a similar phrasing on Rankings (~app.py:12274).
- **Problem**: These sit on pages that are correctly awareness-only (never gate), so the softer language is arguably appropriate there — but it's the one place in the audit where copy tone visibly diverges from the rest of the app's directive voice ("Sell all X shares — mechanical stop rule").
- **Recommendation**: No functional change needed; consider whether "Best practice" framing should be reserved for genuinely awareness-only surfaces (as it is today) versus the directive imperative voice used everywhere a real recommendation fires — if so, this is already correct and can be left as-is.

### I9 — User Guide's 27 expanders are 96% collapsed with no index
- **Location**: [app.py:23042-23716](app.py#L23042-L23716) — only the first two of ~27 expanders default to `expanded=True`.
- **Problem**: For a page meant to be the onboarding reference (per `project_manual` memory: "first-run onboarding sequence"), a new user must expand-and-scan roughly 25 sections sequentially to find a specific answer.
- **Recommendation**: Add a short anchor list / table of contents at the top of the page linking to each expander's topic, or group expanders under a few `st.tabs()` by theme (Getting Started / Scoring & Gates / Pages at a Glance / Glossary) the way other multi-section pages in the app already do.

### I10 — Duplicated email-rendering helpers risk visual drift between two peer reports
- **Location**: `stock_analyzer/notify.py` — `_md_inline`/`_section` helpers are duplicated near-verbatim between `render_debrief_email` (~L545-635) and `render_intelligence_email` (~L692-763); the two templates' footer disclaimers also differ slightly (weekly debrief: "Not financial advice"; monthly report: "Surfaces patterns; never changes a gate · Not financial advice").
- **Problem**: A user who reads both the weekly debrief and monthly report as companion pieces could notice inconsistent formatting or disclosure if one helper is fixed and the other isn't, since any future markdown-rendering bugfix must be applied twice by hand.
- **Recommendation**: Extract the shared helpers into one function reused by both templates. Confirm the footer difference is intentional (the monthly report's extra caveat may be deliberate given its stricter LLM-boundary contract) and, if so, leave it — otherwise unify.
