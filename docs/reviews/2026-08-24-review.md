**Recommended next action:** fix finding #1 first (it silently corrupts a real financial number with no user-visible symptom until someone reconciles against Robinhood by hand), then #2 (cheap, a few-line fix), then decide whether to fold in the pre-existing XSS fix at the same time since it's a one-line `html.escape()` matching an existing pattern already used elsewhere in the same file.

## 4. High-priority issues

**1. `account_flows` deposits/withdrawals have no dedup key — re-inserted on every broker sync, corrupting Modified-Dietz net-contributed-capital.**
`cron_runner.py:1878-1882` → `stock_analyzer/db.py:3761-3779` (`add_account_flow`) → `stock_analyzer/broker_sync.py:394-404` (`classify_transactions`' `flows` bucket).

Verified against HEAD: `classify_transactions` builds a `flows` entry for every `CONTRIBUTION`/`WITHDRAWAL` SnapTrade activity in the sync window — unlike BUY/SELL (two-tier dedup) and `income_events` (`snaptrade_txn_id` upsert), it attaches no id and is never checked against previously-seen flows. `db.add_account_flow` (confirmed lines 3761-3779) does a bare `.insert()`, and the `account_flows` DDL (`db.py:378-385`) has only an identity PK — no unique constraint on any combination of columns. The cron re-fetches a rolling `SNAPTRADE_SYNC_MAX_TXN_LOOKBACK_DAYS = 90`-day window and fires twice daily (`system_health.py`'s `broker` lane, `"0 16,21 * * *"` UTC). Confirmed live at `cron_runner.py:1878-1882` — every element of `classified["flows"]` gets its own unguarded `db.add_account_flow(...)` call every run.

**Consequence:** the first time SnapTrade reports a real contribution or withdrawal, it gets re-inserted roughly twice a day for up to 90 days — up to ~180 duplicate rows per real cash event. `account.net_contributed_capital` sums every row in `account_flows`, so NCC inflates without bound, and `account_growth`/`growth_pct` (the headline return number, and the basis the Forward Portfolio Simulator and other performance surfaces replay against) silently understates real return — potentially flipping a genuine gain into an apparent loss. Fails **open** (no error, no banner), and both `cron_runner.py` and `db.py` are `_GATE_FILES` entries.

**Fix:** add a `snaptrade_txn_id` column + partial unique index to `account_flows` (mirroring `snaptrade_income_events`, `db.py:723-734`), thread the id through `classify_transactions`' `flows` entries, and change the SnapTrade-sourced write to `upsert(..., on_conflict="snaptrade_txn_id", ignore_duplicates=True)`. Leave the manual/baseline `add_account_flow` call site (`app.py`'s deposit-logging UI) on the id-less plain insert — this bug is specific to the broker-sourced path re-scanning the same window repeatedly.

**2. The F-253 Margin Call Distance panel silently doesn't render if 💰 Account is opened before 🏠 Home this session.**
`app.py:29227-29230` (consumer, verified) vs. `app.py:4599-4620` (sole producer, gated inside `if page == "🏠 Home":`).

Verified against HEAD:
```python
_lev_c = st.session_state.get("_leverage_cache")
if _lev_c is None:
    _lev_c = {}
if _lev_c.get("levered"):
    ...  # renders the 📐 Margin Call Distance section
```
`_leverage_cache` is written **only** on Home's render path. A session that lands on 💰 Account first — direct bookmark, browser refresh while on Account, or simply never having visited Home yet this session — sees `_lev_c = {}`, `.get("levered")` is falsy, and the entire Margin Call Distance panel is skipped with no banner, no caption, nothing. Two lines above this same block (`app.py:29205`, verified: `_levered = _cash < 0`), the page **independently and correctly** computes leverage fresh from `db.load_account_cash()` and renders the margin-debit caption — so the user is told "⚖️ Margin debit $X — you hold $Y of stock on $Z of your own money" immediately above a call-distance section that just isn't there, with no indication why. This is the exact "silently filter, no banner" pattern CLAUDE.md's coding conventions explicitly prohibit ("For UI suppressions, render a visible banner explaining what was suppressed and why — never silently filter").

**Fix:** distinguish "key absent, never computed this session" from "computed and confirmed not levered." Cheapest option: since Account already independently recomputes `_cash`/`_equity`/`_levered` fresh (it doesn't depend on Home having run), compute the `call_distance` inputs inline here too rather than depending on `_leverage_cache`. Alternative: render an explicit one-line caption ("Margin awareness not yet computed this session — visit 🏠 Home to populate it") when the key is absent, so the gap is visible rather than silent.

**3. (Pre-existing, not introduced in this window — flagged opportunistically) Unescaped ticker interpolation in the Trade Journal SELL-confirmation wash-sale banner.**
`app.py:22907-22917`, confirmed still live via direct read; confirmed pre-existing via `git show d919469e14af685a6ce9896846918fe3468656c8:app.py` showing the same unescaped interpolation at the base commit.

```python
st.markdown(
    f"...🧾 <b>Wash-sale watch:</b> you bought {_ps_ticker} "
    f"{_ws_days} day{'s' if _ws_days != 1 else ''} ago ...",
    unsafe_allow_html=True,
)
```
`_ps_ticker` (`app.py:22881`, from `st.session_state["_tj_pending_sell"]["ticker"]`) traces back to `ticker_input = (st.session_state.get("_tj_ticker") or "").strip().upper()` (`app.py:23823`) — free user text typed into the Trade Journal's ticker box, with no HTML-safety transform before this render. This is the exact class the codebase itself calls out and has fixed 7 times elsewhere in this file (e.g. `app.py:26131-26137`'s `_action_esc`/`_ticker_esc`, `app.py:7920`'s `_safe_html`). Single-user app, so real-world exploitability is limited to self-XSS, but it's a live instance of a named, tracked bug class.

**Fix:** `html.escape(_ps_ticker)` before interpolation, matching the pattern already in use two of the same file's other 6 fixed instances.

## 5. Medium-priority issues

- **`cron_runner.py:1724-1766, 1831-1850, 1864-1888` — broker balance/transaction sync can select the wrong SnapTrade account when the heaviest account's read times out but a near-empty auxiliary account (credit card / crypto / IRA) responds.** The position-snapshot write is correctly guarded (`if _pos_read_failed:` skips it), but account selection for balance sync and transaction import (`_best_id` = account with the most positions **among those that responded**) isn't: if the real brokerage account times out (the code's own comment at `1780-1781` names it "the slowest read and so the likeliest to hit `SNAPTRADE_REQUEST_TIMEOUT_SEC`") while an aux account with 0 positions responds, `_best_id` becomes that aux account and both `save_account_cash` (`1839`) and `get_account_activities` (`1865`) run against it — silently overwriting the real margin-debit `account_cash` with the aux account's balance. This feeds `_leverage_cache` and the whole F-253/F-254 margin-awareness surface, so a transient timeout on the heavy account can flip "levered" to false or distort the leverage ratio until the next clean sync. **Fix:** when `_pos_read_failed` is true and the selected `_best_count == 0`, treat selection as ambiguous and skip balance/transaction sync (notify + `return 1`) rather than syncing against the aux account.

- **`tests/test_margin.py:176-198` — the gate-isolation test for `margin.py` is weaker than its own comment claims.** It asserts `not hasattr(mod, "capital_basis_weight")` on each gate module, which only catches `from stock_analyzer.margin import capital_basis_weight`, not the module-alias style (`import stock_analyzer.margin as m; m.capital_basis_weight(...)`) that `app.py` itself actually uses (confirmed: `app.py` imports margin as `_margin_mod`). It also only covers `capital_basis_weight` (not the equally awareness-only `call_distance`), and its `gate_modules` list omits 5 of the 14 `_GATE_FILES` entries (`risk`, `valuation`, `technicals`, `fundamentals`, `bundle_loader`). The design invariant currently holds in practice — confirmed by direct grep, `stock_analyzer.margin` is imported only by `app.py`'s render layer and the tests — so this is a test-integrity gap, not a live bug, but it means the test would stay green even if a future gate file adopted the alias-import style. **Fix:** assert on the actual import graph (e.g. via each gate module's compiled import list) rather than `hasattr`, extend to `call_distance`, and complete the `gate_modules` list.

- **`stock_analyzer/debrief_advisor.py:280-333` — the new "protective signals" weekly-debrief block (symmetric WATCH/TRIM/EXIT reporting) has zero test coverage.** `tests/test_debrief_advisor.py` was not touched in this window and has no reference to `protective_signals` or `exit_signals_df`. The tier-escalation merge logic (`_prot_by_tk` — keep the highest-severity tier across possibly-unsorted rows, exclude `closed_tickers`, dedupe) is exactly the kind of stateful accumulation logic that regresses silently. Worth at least 3 tests: tier escalation across out-of-order rows, a ticker present in both `closed_positions` and this week's exit signals (must be excluded), and the `sold` flag when a SELL trade coincides with a signal.

- **`scripts/check_antipatterns.py`'s `OFFLINE_SENTINEL_COLLAPSE` detector only matches the `ast.BoolOp`/`Or` form (`x.get(...) or {}`), not the semantically identical ternary form (`x.get(...) if <cond> else {}` / `{} if <cond> else x.get(...)`).** A scripted AST scan for the ternary shape across the whole tree found one new instance this window, `app.py:6201-6202` (`_bd_diff.get("qty_mismatch", []) if isinstance(_bd_diff, dict) else []`, from the F-252 broker-drift cross-reference work) — currently benign (verified: `broker_sync.decide_drift_banner()` guarantees `diff` is a real dict whenever the guarding `state == "drift"` condition holds, so the `else []` branch is unreachable today), but the detector's blind spot is real and matches exactly the bug class it exists to close. This is the same shape of meta-finding the 2026-08-05 audit made about this same gate ("the gate's own detectors are narrower than the bug classes they're named after") recurring for a second time in 3 weeks. **Fix:** add an `ast.IfExp` visitor mirroring the existing `BoolOp` one, reusing `_has_get_call`/`_is_empty_container`.

- **`app.py:11002` / `app.py:26704-26723` — an undocumented cross-page coordination cache key, `_rh_prices_cache_{start_date}_{end_date}`, shared by Summary's Engine Track Record card and the Recommendations History page (deliberate first-writer-wins design per an inline comment at `10979-10985`), is not in CLAUDE.md's documented session-state cache-key list.** This is a genuine two-feature publish/consume key per CLAUDE.md's own coordination-pattern definition, just one that slipped the list (nothing mechanically enforces this one, unlike `constants.py`). **Fix:** add a row to CLAUDE.md's coordination-cache paragraph.

## 8. Systemic observations

- **A "gate-dodging refactor" pattern appeared this window and is worth watching for going forward.** `app.py:12625`'s leverage-cache read was changed from `st.session_state.get("_leverage_cache") or {}` to `_lev_c = st.session_state.get(...); if _lev_c is None: _lev_c = {}` — syntactically different (dodges the antipattern gate's literal `or {}` match) but semantically identical (both still collapse "never computed" into "computed, empty"). The same collapse, now happening at a site the deterministic gate can't see, is exactly what caused Finding #2. A deterministic AST gate catches syntax, not semantics — when a fix changes the *shape* of an antipattern instance without changing its *behavior*, it should be treated as unresolved, not fixed.
- **The antipattern gate's own detectors keep having narrow-syntax blind spots, one release after another.** This is the second consecutive audit (2026-08-05, now 2026-08-24) to find a detector that's narrower than the bug class it's named after (`IfExp` vs `BoolOp` this time; two-arg `.get()` and bare-name-helper HTML last time). Worth a dedicated pass hardening all 4 detectors against every syntactic form of their named bug class in one sitting, rather than discovering gaps one audit at a time.
- **💰 Account has grown to recompute some state fresh (cash, equity, leverage-from-scratch) while depending on Home-only caches for other state (`_leverage_cache`'s derived fields) on the same page, in the same visual section.** That seam is exactly where Finding #2 lives — the fresh computation renders correctly while the cache-dependent panel beside it silently vanishes. Not necessarily wrong to mix the two (some things genuinely are cheap enough to recompute per-page), but any panel added to Account going forward should explicitly decide which category it's in rather than inheriting whichever pattern happens to be nearby.
