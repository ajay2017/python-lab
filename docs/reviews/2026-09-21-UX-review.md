## Executive Summary

The copy discipline that made the last two reviews close cleanly is still holding under real scale — 26 days and roughly 250 files changed, and every prior fix independently verified still live. The gap is that **two bug classes this app has already fixed once are reopening on every new surface that ships, because the fix lives at the old call site, not in a convention new code automatically inherits.** The Account page's privacy mask was fixed on Cash Activity in commit `f585005`, then again didn't apply to Broker Sync (fixed 2026-08-27), and now doesn't apply to the two brand-new Reports tabs (Tax Report, Performance Review) — three strikes on the same page. Separately, the Risk Analysis Dashboard captions raw margin-debit exposure as "your equity" using the exact session-state key `beta_repair.py`'s own new docstring calls "a documented footgun" a few hundred lines away in the same file. The single biggest opportunity: **make the fix a helper/convention new render code can't skip, not a per-site patch** — a shared `_dollar()`/`_pct_of_equity()` wrapper for anything reading `_leverage_cache`, and a lint-style habit (or the antipattern gate) that flags a new `st.metric(f"${{...}}")` on 💰 Account without a nearby `_m()` call.

## Critical Issues (act now)

### C1 — The two brand-new 💰 Account → 📄 Reports tabs leak every dollar figure through privacy mode, again
- **Location**: `app.py:35211`, `35233`, `35318-35328`, `35417-35429` (Tax Report + Performance Review tabs, F-276/F-276b, shipped 2026-09-18)
- **Problem**: Confirmed by direct grep across the full tab block (`app.py:35033-35479`, ~450 lines): **zero** occurrences of `_m(`, `_privacy`, or `_chart_priv`. Every realized-P&L figure, cushion number, and gain/loss dollar amount renders via bare `st.metric(f"${...}")`/`st.dataframe(...)`. Toggling "🙈 Hide values" masks the rest of 💰 Account — the KPI tiles, Capital Trend chart, and (since 2026-08-27) Cash Activity — but not this tab. This is the third time this exact gap has appeared on this one page: the 2026-08-04 review found it on the KPI tiles (fixed), the 2026-08-26 review found it on Cash Activity (fixed 2026-08-27), and it is now open a third time on the newest tab.
- **Recommendation**: Wrap every dollar figure in both Reports sub-tabs with `_m()`, matching the pattern already established at `app.py:34785`/`34903-34924`. Given this is the third recurrence on one page, also consider a structural fix: a small `_acct_metric($, ...)` helper that always routes through `_m()`, so a future tab can't omit it by simply not knowing the convention exists.

### C2 — 🔗 Risk Analysis's leverage caption reads the exact cache key its own new sibling code calls "a documented footgun," and labels gross book value as "your equity"
- **Location**: `app.py:14232-14247` (the sector-shock leverage caption); the mislabeled key's producer at `app.py:5099` (`"equity": float(total_val)`, i.e. gross holdings market value, not equity); the warning it contradicts at `stock_analyzer/beta_repair.py:355-358`
- **Problem**: `_lv_eq = _f(_lev_c.get("equity"), 0.0)` reads `st.session_state["_leverage_cache"]["equity"]` directly, then captions a sector-shock dollar impact as `f"(−{_lv_eq_pct:.0f}% of your equity)"`. But `beta_repair.py`'s docstring — new this window, added specifically to prevent this — states verbatim: *"`_leverage_cache`, whose 'equity' key is actually the gross book, not equity (a documented footgun) — the caller must resolve net_capital independently."* On this owner's measured book (gross book ~$24,503 vs. net capital ~$7,802), the caption understates the real percentage-of-capital impact by roughly 3x. The irony: `app.py:15080`, a few hundred lines away in the same file, correctly resolves `net_capital` via `margin.resolve_net_capital` for the exact same kind of caption, per the terminology discipline F-253/F-254/F-255 spent multiple commits establishing.
- **Recommendation**: Route this caption through `margin.resolve_net_capital`/`capital_basis_weight` the same way the beta-repair site a few lines below it already does, rather than reading `_leverage_cache["equity"]` directly. This is a same-file, same-page inconsistency — the correct pattern already exists a few hundred lines down.

## Improvements (high value, not blocking)

### I1 — Both retrospective ledger pages leave "Building" undisclosed as an expected multi-month state until the reader scrolls past every card
- **Location**: 🛑 The Road Not Taken (`app.py:32211-32216`, with the only timeline disclosure at `32264-32269`); 🎯 Recommendation Outcomes (`app.py:32385-32396`, same gap)
- **Problem**: Per CLAUDE.md, most gates on both pages are *expected* to read "Building" for roughly two months by design — that's not communicated anywhere near the top of either page, only in a retirement-criterion footnote below every card. A first-time viewer seeing every row stuck at "Building" for weeks has no on-page signal distinguishing "working as designed, wait" from "something is broken."
- **Recommendation**: Add one shared caption near the top of both pages (ideally identical wording, reused as a helper) — e.g. "Expect most rows to read Building for the first couple of months after this page ships — that's by design, not a fault."

### I2 — Portfolio Investigator never states its scope boundary until a question is refused
- **Location**: `app.py:40643-40648`
- **Problem**: The example-question caption shows 4 sample prompts but no statement of what the tool *can't* answer — a user only learns the boundary by triggering a refusal.
- **Recommendation**: Add one line, e.g. "Answers questions about your own trading history and portfolio state — not general market or stock questions."

### I3 — Research-a-Stock silently picks one match on an ambiguous company name, with no disclosure that alternatives existed
- **Location**: `stock_analyzer/ticker_resolver.py:63-70`; confirmation caption at `app.py:7791-7795`
- **Problem**: `resolve_company_name` always takes the single top-scored match. The confirmation caption ("Showing results for **{symbol}** — {name}") correctly discloses *what* was picked (this is a real strength — the resolved ticker is never silently substituted), but not *that a choice was made among alternatives* when a query like "Alphabet" could plausibly mean GOOGL or GOOG, or a common name matches multiple small-caps.
- **Recommendation**: When ≥2 equities score within a small margin of each other, append "(other matches: X, Y)" to the confirmation caption.

### I4 — Two raw exception strings ride alongside otherwise-clean fallback messages
- **Location**: Ask tab, `app.py:40413`/`40421` + `stock_analyzer/portfolio_qa.py:356,1115` (a `st.caption(f"Details: {round_['details']}")` appending the raw `f"{type(e).__name__}: {e}"[:300]`); Research-a-Stock's load-failure path, `app.py:7796-7797` (`st.error(f"Could not load data for {ticker}: {error}")` interpolating the bare caught exception)
- **Problem**: Both primary messages are well-written clean fallbacks, but a raw provider/library exception string is visually present at the same level immediately below or inside the same sentence — provider SDK jargon reaching a user-facing surface.
- **Recommendation**: Move the raw detail into a collapsed `st.expander("Technical details")` on the Ask tab; map common Research-a-Stock failure classes (no data / delisted / non-US ticker) to plain sentences instead of the bare exception text.

### I5 — The Risk Analysis Dashboard leverage caption and the beta-repair candidate ranker use inconsistent vocabulary for the identical "stale cash balance" state
- **Location**: `app.py:15068-15071` ("Leverage impact of this trim can't be measured this session — no fresh cash-balance figure on file") vs. `app.py:16681-16685` ("Margin Call Distance withheld — your account's cash balance is stale")
- **Problem**: Same underlying `basis == "stale"` condition, worded two different ways ("can't be measured" vs. "withheld... stale") across two sibling surfaces a user could see in the same session.
- **Recommendation**: Pick one phrasing and reuse it verbatim at both sites.

### I6 — Two adjacent User Guide tooltips define "high correlation" with different numeric boundaries for the same underlying metric
- **Location**: `app.py:922-932` ("Portfolio Correlation": <0.30 well-diversified, 0.30-0.60 Moderate, >0.60 High) vs. `app.py:934-944` ("Diversification Score," updated this window off `DIVERSIFY_WELL_PCT`/`DIVERSIFY_MODERATE_PCT`: ≤0.16 well-diversified, 0.16-0.40 Moderate, >0.40 High)
- **Problem**: Both describe average pairwise correlation, back-to-back in the same glossary, with different cutoffs — a user reading both gets two different definitions of "High Correlation Risk."
- **Recommendation**: Either derive "Portfolio Correlation"'s bands from the same constants as "Diversification Score," or add an explicit note that the two intentionally use different bands and why.

### I7 — The beta-repair candidate ranking's sort concept is used but never defined
- **Location**: `app.py:15419-15423` ("ranked by beta relief, correlation to your book, then composite")
- **Problem**: "Beta relief" ranking is named once and never explained before the β/correlation/composite columns appear beneath it.
- **Recommendation**: A one-line `help=` or caption: "candidates that reduce your book's beta the most, cheapest first."

### I8 — The 2026-09-20 protective-track-record disclosure lives only on 🧾 Summary, not on 🏠 Home
- **Location**: `app.py:11936-11973` (the sole instance, confirmed via full-file grep)
- **Problem**: Per the user-manual, Home is the "look here first, every day" surface, and Summary is the secondary cockpit. A Home-only session never sees this caveat even when its gating condition (`band=="firm"` + negative `protect_alpha`) fires.
- **Recommendation**: Not a bug to silently fix — this is a scope decision the owner should make deliberately (mirror to Home vs. deliberately Summary-only), flagged here so it isn't an accidental gap.

### I9 — `watchlist_advisor.py` hand-types the composite gate thresholds it also imports as constants
- **Location**: `stock_analyzer/watchlist_advisor.py:313,333` (literal `44`, duplicating `COMPOSITE_HOLD = 44`); `:413,483,557,602,643` (literal "above 65 threshold" ×5, duplicating `COMPOSITE_BUY = 65`)
- **Problem**: Pre-existing (2026-05-07/05-11, outside this window's diff), but exactly the "hand-typed duplicate of a constant" class this project has hit and fixed before (2026-08-04 review, I7) — if either constant is ever repriced, these six strings go silently stale.
- **Recommendation**: Format from `constants.COMPOSITE_HOLD`/`constants.COMPOSITE_BUY` instead of the literals.
