## 1. Executive summary

The codebase is, for its size (~40.8k LOC, `app.py` alone ~17.8k), unusually disciplined. The decision spine is clean: `constants.py` is a true single source of truth with policy rationale on every gate; the scoring/recommendation boundaries are imported, not duplicated; the advisors (`exit_advisor`, `concentration`, `recommendations_history`) carry safe-by-construction reasoning and a consistent "withhold rather than fabricate" posture. The read-only write-guard, secret redaction, and analytics-integrity discipline are genuinely strong. **No critical, ship-blocking defect was found.**

The real risk lives in the **second runtime** (the headless cron) and at the **data boundary**, where hardenings that exist on the primary path were not uniformly extended to sibling paths:

- **Top risk — silent loss of an unattended deliverable.** The EOD pullback lane records its dedup state even when the email send fails, so a transient Resend failure suppresses that day's pullback email entirely (the other two cron lanes correctly gate the save on success). Compounded by the absence of any dead-man's-switch — a broken cron is invisible.
- **Second risk — cross-source recommendation drift.** When FMP serves a ticker's fundamentals, the forward-P/E valuation leg silently drops out of the composite, so the *same* ticker can score differently (and flip Buy↔Hold) purely on which provider answered — the exact failure the multi-source layer was meant to prevent.
- **Third risk — unbounded hang.** The primary data path (yfinance) has no request-level timeout; in the unattended cron a stuck socket burns the whole job budget.

Recommended next action: fix the one-word EOD dedup regression (High #1), add a cron failure notification (High #2), and make a deliberate policy decision on the FMP forward-P/E gap (High #4 — it changes a score, so it is the user's call, not a unilateral code fix).

Counts: **0 critical · 5 high · 9 medium · ~12 low/nits.**

## 3. High-priority issues

### H1 — EOD pullback dedup is written even when the email fails to send → silent suppression for the day
`cron_runner.py:171-175` (verified against source)

The EOD lane calls `db.save_alert_state(today_str, "pullback", _EOD_ROW)` **unconditionally** right after `sent = _send_email(...)`, with no check on `sent`:

```python
subject, html = render_pullback_email(pb, payload.get("built_at", today_str))
sent = _send_email("pullback", subject, html)
if db.save_alert_state(today_str, "pullback", _EOD_ROW):   # ← not gated on `sent`
    _log(...)
```

If Resend returns non-200 / times out / raises, `_send_email` returns `False`, but the "emailed today" marker is still written. The later straddling-DST EOD slot — which exists to retry — then hits `state.get("last_emailed_date") == today_str` (line 169) and skips. The pullback drawdown email is lost for a real ≥3% down-day.

**Why it matters:** This directly contradicts the documented retry-on-failure contract the *other two* lanes follow. The premarket lane (124-133) saves only `if sent or not alerts`; the buy lane (275-278) saves only `if sent and ...` — both with explicit comments that this is precisely so a transient Resend failure is retried by the later slot. The EOD lane was not given the same guard. A `~3%` index day happens only a few times a year, so each lost occurrence is high-cost.

**Minimal fix:** gate the save on success, mirroring the buy lane:
```python
if sent and db.save_alert_state(today_str, "pullback", _EOD_ROW):
    _log(...)
elif not sent:
    _log("pullback email not sent — state NOT saved so later slot can retry.")
```

### H2 — No dead-man's-switch: a broken cron is invisible
`.github/workflows/alerts.yml` (whole file) + all `cron_runner.py` lanes (each `return 0`)

Every lane swallows its own faults and returns 0 (e.g. `compute_protective_alerts` collects errors into `errors[]` and returns normally; `_run_scan` catches and returns 0). The workflow has no `if: failure()` step and no success-heartbeat. So the Actions run shows green even when every provider failed from the datacenter IP and zero alerts were computed — and the only way the user learns the pipeline stopped is by manually opening the Actions tab. GitHub also silently disables scheduled workflows after 60 days of repo inactivity.

**Why it matters:** the product's entire value is *unattended* delivery of protective signals; there is currently no path by which the user finds out delivery has stopped.

**Minimal fix:** add an `if: ${{ failure() }}` step that emails via the existing Resend secret, and/or have `main()` emit a periodic "ran, computed N alerts, sent=…" heartbeat whose *absence* is the signal. Set a non-zero aggregate exit code on lane failure so Actions marks the run failed.

### H3 — yfinance calls have no request-level timeout → unbounded hang in the unattended cron
`stock_analyzer/providers/yfinance_provider.py:37-40` (documented in-code), exercised by every cron data path: `fetch_ticker_bundle`/`load_bundle`, `fetch_spy`/`fetch_vix`, `fetch_market_indices`, plus the direct `yf.download(...)` calls in `cron_runner.py:407,523`.

The keyed providers (Finnhub/FMP) all use `http_get_json` with a 10s timeout (`providers/_util.py`); only the **primary** (yfinance) path is unbounded. Failover triggers on *exception*, not on *hang* — so a stuck TCP socket is bounded only by the 15-min job timeout, which then kills the job mid-run leaving partial state (and, pre-H1-fix, dedup recorded but email unsent).

**Why it matters:** reliability — the one path with no time bound is the one most likely to hang, and it defeats the failover design.

**Minimal fix:** wrap yfinance fetches in a hard wall-clock cap (`concurrent.futures` per-ticker timeout) so a hang raises and lets the orchestrator fail over; at minimum lower the workflow `timeout-minutes` so a hang fails fast and is retried by the next slot.

### H4 — FMP-served fundamentals drop the forward-P/E valuation leg → silent cross-source composite drift
`stock_analyzer/providers/fmp_provider.py:341` + `stock_analyzer/data.py:203` + `stock_analyzer/fundamentals.py:162` (verified against source)

FMP's `_build_info` sets `info["trailingPE"]` but never `info["forwardPE"]`. `data.py:203` maps `"forward_pe": info.get("forwardPE")` → `None`. In `fundamental_score`, the valuation block is gated `if fwd_pe and fwd_pe > 0: max_points += 20` (fundamentals.py:162) — so for an FMP-served bundle the 20-point valuation leg is excluded from **both** `points` and `max_points`, and the score becomes the average over the remaining legs. The same ticker therefore scores differently when served by FMP vs yfinance, and can cross the Buy(65)/Hold(44) boundary on provider identity alone. `forward_pe` is also one of the five `CORE_FUNDAMENTAL_KEYS`, so the gate metric count drops 5→4 — but `FUNDAMENTALS_GATE_MIN_METRICS=1` still passes, so nothing withholds and the drift is invisible.

**Scope/likelihood:** only on the FMP-served-`.info` path (yfinance `.info` sparse → FMP backfill, or FMP failover). Not the healthy yfinance path. But that path activates precisely for the sparse-`.info` tickers the backfill exists to rescue.

**Why it matters:** "the same name flips Buy↔Hold depending on which source answered" is exactly the inconsistency the multi-source layer was built to prevent, and it happens silently — contrary to the "decides, does not inform / recommend nothing rather than wrongly" posture.

**Fix is a policy decision (Opus-lead / user's call, not a unilateral edit):** options are (a) populate `info["forwardPE"]` from an FMP forward-estimate field, (b) fall back `forwardPE = trailingPE` when forward is unavailable (a deliberate, documented scoring choice), or (c) accept the dropped leg and document it. Each changes a composite, so it belongs with the user.

### H5 — Orchestrator history failover has no usability floor → garbage payload accepted as success
`stock_analyzer/providers/orchestrator.py:99-106, 142-149`

The "usable result" tests are only: not None, not empty DataFrame/list/dict. A history frame that is structurally valid but garbage — a single ancient row, all-stale bars, all-zero/negative closes — passes the guard and is returned as authoritative; failover never advances to the next provider. `get_bundle` checks only `hist.empty`, not whether Close is usable. There is no min-row / NaN-ratio / positive-price floor.

**Why it matters:** this is the "structurally-valid-but-garbage payload poisons downstream scoring" class. Partially mitigated downstream (`technicals.compute_indicators` strips NaN-Close bars), so the all-NaN case is caught — but a too-short or all-stale frame still scores.

**Minimal fix:** add a usability predicate (e.g. `≥ N` non-NaN positive Close bars, N a named constant in `constants.py`) to `_failover_single` and `get_bundle`; below it, treat as empty and fall through.

## 4. Medium-priority issues

### M1 — Risk-advisor failure sets the HIGH-alerts gate cache to `[]` (fail-open on a suppression), with no offline banner
`app.py:2576-2582`

If `build_risk_advisor_recommendations` throws, the `except` sets `_risk_advisor_recs = []` and then `_risk_high_alerts_cache = []`. The Watchlist consumer (`app.py:~11995` → `watchlist_advisor.build_watchlist_recommendation(active_high_risk_alerts=...)`) reads an empty list as "no active HIGH risks → don't suppress ENTER_NOW." Unlike the `_grow_today_sectors_cache` / `_daily_brief_offline` pair (which set `None` on failure and render an explicit offline banner), this cache has no offline sentinel, and `_daily_brief_offline` is set by a *separate* try/except — so a risk-advisor-only crash silently disables the suppression with no banner.

**Minimal fix:** on the except, set `_risk_high_alerts_cache = None` and have the Watchlist treat `None` as "risk coordination offline" in the same banner family as `_grow_today_sectors_cache is None`. (Matches the documented house contract: producers fail to `None`, not an empty container.)

### M2 — `prev_close` defaults to the live price → silently disarms the strict cross-check leg
`stock_analyzer/providers/finnhub_provider.py:62`, `fmp_provider.py:150`, `yfinance_provider.py:242`

When a source omits `prev_close`, all three set `prev = price`. The cross-check's *strict* prev-close leg (`DATA_XCHECK_PREVCLOSE_TOL_PCT = 0.5%`) is the high-signal integrity check (missed split / wrong-symbol / poisoned feed). If either side's prev_close fell back to its own live price, that leg compares live-vs-live and passes even when the settled closes genuinely disagree — leaving only the 3% loose leg. The derived `change_pct` is then computed off `prev == price` → reports 0.0% for a real mover.

**Minimal fix:** keep `prev_close = None` when the source omits it; the cross-check already guards `if primary_prev_close and other_pc`, so the leg will skip cleanly; compute `change_pct = None` rather than 0.0 when prev is unknown.

### M3 — `crosscheck_price` (single-ticker) is not gated on validator health; only `crosscheck_batch` is
`stock_analyzer/providers/orchestrator.py:248-298` vs `322-370`

`crosscheck_batch` skips a validator that is `_is_red` (the documented false-alarm fix during a Yahoo 401/crumb/429 degradation). The single-ticker `crosscheck_price` has no equivalent guard, so it can compare against a degraded validator and return a "sources disagree" — the very false integrity banner the batch gate prevents. **Verify the live exposure** (see Open Questions): if no live caller uses `crosscheck_price` vs the batch path, this is latent.

**Minimal fix:** skip `_is_red` providers in the single-ticker validator selection; if none remain, return `None` (no opinion), not a disagreement.

### M4 — Sunday cron lane has no error isolation between its three chained jobs
`cron_runner.py:605-609`

`main()` calls `_run_thesis`, `_run_debrief`, `_run_monthly_report` sequentially with no per-call try/except and discards the first two return values. Most internals are individually guarded, but not all call sites (`build_debrief_package`, `build_report_package`, the `save_*` writes). If one raises, the next two never run — and on the first Sunday of a month the monthly report (the most valuable of the three) is last in line.

**Minimal fix:** wrap each of the three calls in its own try/except; aggregate a non-zero exit if any failed (feeds the H2 dead-man's-switch).

### M5 — LLM calls have no explicit timeout
`stock_analyzer/thesis_advisor.py:181` & `:405`, `debrief_advisor.py:288`, `intelligence_report.py:372`

`client.messages.create(...)` is called with no `timeout=`/`max_retries=`. The thesis lane makes one call per open position in a loop; on a busy Sunday a slow/hung response, multiplied across positions plus debrief + monthly, can run long with only the 15-min job timeout as backstop. All are wrapped in try/except→None, so correctness is contained — this is a reliability/latency item.

**Minimal fix:** pass an explicit `timeout=` and small `max_retries` to the Anthropic client / `.create` call.

### M6 — yfinance providers don't strip NaN-Close at the boundary (inconsistent with FMP)
`stock_analyzer/providers/yfinance_provider.py:69-74, 77-82`

`fmp_provider.price_history` does `.dropna(subset=["Close"])` (line 208); the yfinance equivalents return the raw frame. The codebase relies on `compute_indicators` to strip NaN bars, but `fetch_price_history`/`fetch_ticker_bundle` are public and consumed elsewhere (`fetch_spy`, `fetch_vix`) where a `max()`/`.iloc[-1]`/`$`-format on a raw NaN Close hits the `$nan` / NaN-truthy class that resurfaced once already (`project_bundle_load_resilience`).

**Minimal fix:** apply the same `.dropna(subset=["Close"])` in the yfinance provider so both sources emit the same boundary invariant.

### M7 — yfinance batch records `"success"` even after recording per-ticker `"empty"` → pollutes the circuit-breaker/health
`stock_analyzer/providers/yfinance_provider.py:236,254-257` and `192,213-216`

A partial batch (1 good ticker, 20 missing) logs per-missing `record("empty")` then a single blanket `record("success")` that resets `consecutive_errors`. The circuit-breaker (`in_cooldown`) and validator-health gate (`_is_red`) read these counters, so a degrading Yahoo feed can stay "green."

**Minimal fix:** record one health event per batch call based on coverage (empty if no results, success if full, a partial/error signal on poor coverage), not per-missing-ticker plus a blanket success.

### M8 — User free-text rendered via `unsafe_allow_html` without escaping (in-app only)
`app.py:5547-5548` (trade `notes`) and `app.py:4961-4967` (entry `thesis`)

Both interpolate user free-text straight into an `unsafe_allow_html=True` block with no `html.escape()`. The email path (`notify.py`) escapes everything correctly, so the in-app renderer is the inconsistent surface. Practical exploitability is essentially nil (single-user, password-gated, self-authored) — this is primarily a robustness defect: a stray `<`/`>` in a thesis breaks the card layout.

**Minimal fix:** wrap the interpolated text in `html.escape(...)` at both sites (mirror `notify.py`).

### M9 — Variable-options widgets missing / mismatched explicit keys
`app.py:5814` (`selectbox("Select position to drill down", port_df["Ticker"].tolist())` — no `key=`) and `app.py:9381` (the Brief "Model" selectbox keyed `_brief_model` whose options depend on the separately-selected provider, whose per-provider model sets don't overlap).

Per the documented widget-state hazard, auto-keyed or cross-dependent-option widgets drop/reset state when options change. The drill-down has no key (selection can reset after a buy/sell mutates `port_df`); the model selectbox can hold a value that falls out of `options` when the provider changes — the codebase already guards this exact pattern at `app.py:17570` (pops `_mr_period_select` when out of range) but not here.

**Minimal fix:** add `key="_home_drilldown_pick"` at 5814; before the model selectbox, `if st.session_state.get("_brief_model") not in _model_opts: st.session_state.pop("_brief_model", None)`.

## 6. Patterns worth keeping (preserve during refactors)

- **`constants.py` as the single source of truth**, with investment-policy rationale on every gate and explicit "changing this is a policy decision" notes. This is the backbone of the whole "decides, does not inform" posture — do not let literals creep back into modules.
- **"Withhold rather than fabricate."** The fundamentals gate (no fabricated neutral-50), `market_risk_posture` returning `None` when fragility is unknown, the batch cross-check pausing when the validator is red — all refuse to render a falsely confident read. This is the right instinct for a decision app.
- **Safe-by-construction reasoning in the advisors.** `exit_advisor.material_add_window_days` (re-anchoring can only *suppress* a false exit, never manufacture one), `concentration.high_beta_share` (excludes unknown-beta from both numerator and denominator), the ATR-scaled-but-ceiling-capped deterioration floors — each documents *why* the math can't go wrong.
- **Read-only write-guard chokepoint** in `db.py` — verified complete: every user-data writer no-ops on `_READONLY`; only the two system-cache writers are (deliberately, documented) unguarded.
- **Secret hygiene throughout** — URL redaction (`_util._redact_url`), per-provider key replacement in error text, the cron never logging the Resend key, email `Authorization` header rather than URL. No dangerous primitives (`eval`/`exec`/`pickle`/`os.system`/`shell=True`) anywhere.
- **`_build_context` as a true no-raise boundary** + `load_bundle` last-known-good fallback — the cron and app share one prep path that degrades instead of throwing.
- **Navigation discipline** (`_pending_page` indirection, every write followed by `st.rerun()`) and **no module-level def-after-use** — the prod-NameError class is clean.
- **Analytics integrity** in `recommendations_history.py` — distinct-by-ticker (no surfacing inflation), alpha-vs-SPY (judge on alpha not raw %), per-$1k notional (never a portfolio-level counterfactual), maturity gating, and frozen viz snapshots so a monthly report is an immutable artifact.
- **Cross-source cross-check correctly gated on validator health on the batch path**, and **ET-correct date handling** (earnings dates, holiday calendar) — the timezone off-by-one class is largely closed.

## 7. Systemic observations (root causes — more valuable than the line findings)

1. **"A hardening applied to the primary path but not its sibling."** The clearest repeating theme. The retry-on-failed-send contract is in 2 of 3 cron lanes but not EOD (H1); the validator-health gate is on the batch cross-check but not the single-ticker one (M3); NaN-Close stripping is on the FMP provider but not yfinance (M6); `unsafe_allow_html` escaping is on the email path but not the two in-app sites (M8). Each is a good pattern that didn't get propagated to every instance. **Recommendation:** when a guard is added, grep for sibling entry points and apply it everywhere, or factor the guard into the shared helper so a sibling *can't* skip it.

2. **The "fail to `None`, not an empty container" offline contract is documented and mostly honored — but not universally.** It's correct for `_grow_today_sectors_cache`/`_daily_brief_offline` and is the reference implementation; the risk-advisor HIGH-alerts cache (M1) breaks it and fails *open* on a suppression gate. **Recommendation:** audit every producer cache key listed in CLAUDE.md's coordination section for an explicit `None`-on-failure sentinel + a consumer offline banner.

3. **yfinance is the only data path with no time bound.** The keyed providers all carry a 10s HTTP timeout; the *primary* (and the failover trigger is exception-based, not hang-based) has none (H3). The one path most likely to hang is the one with no cap.

4. **Cross-source consistency is enforced unevenly.** The multi-source layer's promise — "the same ticker scores the same regardless of which provider answered" — holds for prices (cross-check) but is broken for fundamentals (H4, the dropped forward-P/E leg). Any field that feeds scoring should be normalized to the same shape across providers, or its absence should withhold rather than silently re-weight.

5. **Side effects are sometimes committed before the action they represent is confirmed.** H1 (dedup written before the send is confirmed) and the snapshot upsert+sweep non-atomicity (low-priority) are the same shape: record-then-act instead of act-then-record. Prefer confirming the side effect, then recording it.
