## Executive Summary

The copy discipline in this app is genuinely unusual — the day-P&L caveats, the broker-drift "not checked" branch and the Self vs Engine head-to-head disclosures are better-reasoned prose than most commercial finance products ship, and the offline-vs-checked-empty contract is honoured by producers almost everywhere. The problem is at the **consumer and summary layer**: the sidebar badge that is meant to be the always-visible "something needs you" affordance folds a real offline sentinel into a silent zero, Home's Brief summary card labels four sections with four names none of which match the section headers below it, and seven user-facing timestamps — two of them explicitly suffixed "ET" — are computed from a naive clock on a UTC container. The single biggest opportunity is to treat **summary and status surfaces as first-class copy**, held to the same bar as the card bodies they point at: today the detail is trustworthy and the things that summarise it are not.

### C1 — Seven user-facing timestamps come from a naive clock on a UTC container, and two are labelled "ET"
- **Location**: `app.py:4343`, `4367`, `6095`, `10155`, `10212`, `10302`, `10716` — rendered at `app.py:2297` (outage banner), `15867` (signal-freshness caption), `23588` (Trade Journal help text), `6095` (Command Center header), and inline on 🏠 Home's AI Snapshot and 🧾 Summary.
- **Problem**: Each of these calls bare `datetime.now()`. Verified evidence chain: no `TZ` variable is set in `railway.toml`, `railway_start.sh`, or anywhere in the repo; `CLAUDE.md` states plainly that "the hosted containers run UTC"; `stock_analyzer/market_time.py`'s own module docstring says the same and exists specifically to replace these calls. `scripts/check_antipatterns.py:201-210` catches `datetime.utcnow()` and `date.today()` but **not** zero-arg `datetime.now()`, so this class passes every gate. The consequences, in order of harm:
  - `app.py:10155` renders `f"Date: {datetime.now().strftime('%A, %B %d, %Y %H:%M ET')}"` and `app.py:10212` renders `datetime.now().strftime("%b %d %Y %H:%M ET")`. **These print a UTC time with the literal characters "ET" appended.** At the time of writing (18:13 EDT) they would read `22:13 ET`.
  - `app.py:4343` is `_signals_computed_at` — the value behind "Signals & scores computed at load time (…)" (`15867`) and "Auto-filled from current portfolio signal if held (as of …)" (`23588`). This is the *one* string whose entire job is telling the user how stale the numbers are, and it reads ~4 hours in the future.
  - `app.py:4367` (`_home_data_outage_at`) times the outage warning at `2297`; `app.py:6095` and `10716` render calendar dates that roll to tomorrow after 8pm ET; `app.py:10302` renders a day-of-week that flips to the wrong day in the same window.
  - I cannot observe the rendered strings (hard rule #3 — the app is never run locally), so the *display* is derived from the mechanism above rather than seen. The mechanism itself is verified in code.
- **Recommendation**: `_now_et` is already imported at `app.py:87`. Replace all seven `datetime.now()` calls with `_now_et()` and keep the existing format strings. Separately, extend `scripts/check_antipatterns.py`'s `NAIVE_DATE_TODAY` visitor to also flag zero-argument `datetime.now()` — that is what stops the eighth instance.

Every one is individually well-reasoned (the comments explaining *why* each says what it says are among the best in the file), and they are the correct response to a wrong number. But two things work against them. First, all five use `st.caption` — the app's smallest, lowest-contrast text style — for what are data-integrity warnings that the app's own convention elsewhere renders as `st.warning`; the only severity signal is the ⚠️ character. Second **[code-inferred]**, they render between the eight-tile KPI row and the Command Center's section divider at `6286`, so on a day when three or four fire, several hundred words of caveat sit between the headline numbers and everything below.
- **Recommendation**: Keep every sentence — none of them is padding. Collapse the group into one `st.warning` when two or more fire, with a one-line lede ("Today's P&L is affected by N data issues") and the individual explanations inside an expander; render a single `st.caption` unchanged when only one fires.

### I8 — The broker-drift exception path routes around the "not checked" message the module already provides
- **Location**: `app.py:4736-4738` vs. `app.py:1003-1016`
- **Problem**: `_render_broker_drift` is a genuinely good design — its docstring explains why silence-when-clean is deliberate, and for `state == "unknown"` it renders *"⚠️ Broker drift **not checked** — no broker snapshot available, so the app can't confirm Portfolio Value matches your broker"* whenever a broker is actually linked. But Home's caller wraps the whole computation in `except Exception: _drift_verdict = None` (`4736-4737`, commented "unknown, not 'clean' — nothing renders"), and the renderer's first line is `if not verdict: return`. So the one case where the check *crashed* is the one case that produces no message, while the milder "no snapshot yet" case gets the warning.
- **Recommendation**: Set `_drift_verdict = {"state": "unknown", "reason": "check_failed"}` on the exception path instead of `None`, so it flows into the branch that already has the right words.

## Patterns worth preserving

Three things I found while looking for problems, which are better than the norm and should survive any remediation pass:

- **`_render_broker_drift` (`app.py:977-1022`) is the model for every status surface in the app.** It distinguishes clean / stale-clean / drift / **not checked**, its docstring argues explicitly why a green "matches your broker" line on every render would be harmful noise, and it suppresses the "unknown" caption when no broker is linked at all — because there is nothing to be unknown *about*. That is three levels of judgment most status banners never reach.
- **The Self vs Engine head-to-head disclosure (`app.py:37270-37294`)** escalates from `st.caption` to `st.warning` precisely when *none* of the compared trades is actually a head-to-head, because a side-by-side then implies a comparison that structurally does not exist. Choosing the louder control based on how misleading the layout is — rather than on how bad the number is — is exactly right.
- **The day-P&L caveat prose (`app.py:6175-6284`)** consistently quotes the dollar magnitude and direction of the error, names the most likely cause, and — in the `qty_drift` case — explicitly defers to the broker banner for any ticker that banner already explains, on the stated reasoning that external ground truth outranks an internal inference. I7 above asks for it to be *packaged* better; not one sentence of it should be cut.
