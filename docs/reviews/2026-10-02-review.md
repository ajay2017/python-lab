## 3. Critical issues

**C1 — A withheld/NaN composite score reaching a DB write silently drops an entire day's exit-signals batch, and can silently discard a paid LLM thesis review.**
`stock_analyzer/portfolio.py:589-590` sets `_score = None` for a withheld holding (no fundamentals, or an ETF with no cost data); `:634`'s `pd.to_numeric(df["Score"], errors="coerce")` turns that into `NaN`. Two producers build raw composite maps straight from `port_df["Score"]` with no NaN guard — `app.py:6422,6447,6468` (interactive path) and `stock_analyzer/headless_alert_engine.py:299-305` (cron path) — both feeding `db.save_exit_signals_batch` (`db.py:3475`), and `app.py:40257` feeds `db.save_thesis_review` (`db.py:2235`). Neither writer calls the existing `_json_safe` helper (`db.py:1853`, already used at 3 other write sites) before upserting/inserting.

**Confirmed mechanism, not hypothetical:** `postgrest-py`'s request builder (`_sync/request_builder.py:61` etc.) passes `json=self.json` directly to `httpx`, whose `encode_json` (`httpx/_content.py:176-178`) calls `json.dumps(..., allow_nan=False)`. A live reproduction (`httpx.Request('POST', url, json=[{'a': float('nan')}])`) raises `ValueError: Out of range float values are not JSON compliant: nan` before any network I/O. `save_exit_signals_batch`'s upsert is wrapped in a bare `except Exception: warnings.warn(...); return False` (`db.py:3551-3554`) — so the *whole batch* (every held ticker's WATCH/TRIM/EXIT signal for that day) silently fails to write, not just the withheld ticker's row, whenever even one holding in the batch has a NaN composite. `save_thesis_review`'s except block (`db.py:2243-2274`) only matches missing-column errors, so a NaN failure falls through uncaught further down — the review is shown to the user but silently never saved, after a real LLM call was made and paid for.

**Why it matters:** `exit_signals` is the data behind the Behavioral Fingerprint exit-side analysis and the Defense facet's protective-track-record verdict (`protect_alpha`) — both already thin on data and already the subject of real trust-calibration work this quarter (`project_investor_maturity_roadmap`). A silently-dropped day doesn't error loudly; it just produces a gap that reads identically to "nothing fired that day."

**Fix:** run every record through `_json_safe` (or an equivalent `{k: (None if isinstance(v, float) and v != v else v) for k, v in record.items()}` pass) immediately before the `.upsert()`/`.insert()` call in `save_exit_signals_batch` and `save_thesis_review`; fix the two producers (`app.py:6422` etc., `headless_alert_engine.py:299-305`) to build the composite map as `{t: (None if pd.isna(v) else float(v))}` rather than passing the raw Series value through. Add a test that pushes a NaN composite through `json.dumps(..., allow_nan=False)` and asserts the sanitized writer survives it. This is a `_GATE_FILES` touch (`db.py`) — needs a mandatory Opus review per Hard Rule #4.

**C2 — The commit hook's push-gate skip marker is written regardless of whether any gate actually ran for that commit.**
`.claude/hooks/pre_tool_checks.py:197-202`: the "record this tree as verified" block (`if _is_plain_commit(tokens): tree = _write_tree(); ... _write_verified_tree(tree)`) sits as a sibling to, not nested inside, the `if need_pytest or need_antipattern:` block above it (lines 188-191) — confirmed by reading the control flow directly. A commit that touches only docs/scripts/other non-tested-non-scanned files sets `need_pytest=need_antipattern=False`, runs no gate at all, and *still* writes the current tree as "verified" purely because it's a plain (non-`-a`/non-`--amend`) commit.

**Why it matters:** the push-time re-check exists specifically, per its own comment (`pre_tool_checks.py:208-210`), to "catch the case where a commit landed before this gate existed, or from another session/tool." If an untested code commit (made outside this hook — a concurrent session, a tool that doesn't trigger it, or a commit predating the hook) sits in history, and the next commit through *this* hook is a plain docs-only commit, the marker gets overwritten to match a tree that includes the never-gated code commit — and the subsequent `git push` sees `head_tree == verified_tree` and skips the full run entirely. This is not a rare edge case: `feat(...)` immediately followed by `docs(...)` is this project's own standard commit pattern (used repeatedly this session for F-286/F-287), and while in THIS session's specific usage the feat commit's own gates genuinely did run first (so no real harm occurred here), the mechanism itself provides no such guarantee in general — a second gap confirmed separately: the marker records the *index* tree (`git write-tree`) while pytest runs against the *working* tree, so "byte-identical tree ⇒ identical verdict" is also false whenever unstaged/untracked files differ from the index at commit time.

**Fix:** only write the verified-tree marker when `need_pytest and need_antipattern` were both `True` *and* `_apply_gate_results` returned success for both — never on a plain-commit-type basis alone. Additionally require a clean, fully-staged working tree (no unstaged diff, no untracked files under `stock_analyzer/`, `tests/`, `app.py`, `cron_runner.py`) before trusting the marker. Correct the hook's own docstring claims (both the "outside commits still fall back" and "same tree means same verdict" assertions are currently overstated — see Low #11 below). This fix, plus High #3/#4 below (bypass loopholes, zero test coverage), should land together since they're all in the same function and currently untested.
