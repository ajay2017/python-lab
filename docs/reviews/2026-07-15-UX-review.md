## Executive Summary

The individual advisor surfaces are well-built for the app's "decides, not informs" posture — most recommendations carry a structured directive/why/trigger (or problem/recommendation/institutional_lens) basis rather than a bare verdict, gates are mostly visible rather than silent, and destructive actions are *mostly* guarded (the Trade Journal's SELL-confirmation card is a good pattern). But a handful of concrete defects undercut that posture: a raw SQL `DELETE` statement and a raw Python dict-key leak ("capped by business_quality (42)") are shown directly to the end user, three sibling modules carry duplicated/contradictory hardcoded overweight-trim thresholds that could recommend differently for the same portfolio state, and one module (`earnings_advisor.py`) resurrects a "composite ≥ 68" magic number that a sibling module's own code comment says was deliberately removed for contradicting the scoring scale. The single biggest opportunity, though, is terminology: this audit counted 8+ overlapping severity/action vocabularies and found the word "Watch" alone carrying five distinct meanings across pages — CLAUDE.md already flags a full terminology-consistency sweep as a deferred, scoped-out task, and this audit's per-page inventory (§ Consistency Audit) is ready-made input for that pass.

## Critical Issues (fix before launch)

### C1 — Raw SQL `DELETE` statement + a hardcoded historical cutover date shown as end-user guidance ✅
> **Fixed** — commit b2e347c · 2026-07-15. SQL snippet and "fixed today" framing removed; replaced with a plain "early rows may look sparse — expected" explanation.

- **Location**: [app.py:19083-19087](../../app.py#L19083-L19087) (📜 Recommendations History, "ℹ️ How to read this table" expander); the surrounding prose at [app.py:19081](../../app.py#L19081) also hardcodes the cutover date `2026-05-27` and references "the old verdict logic... fixed today."
- **Problem**: The help expander tells the user, verbatim: *"To clear out the early sparse rows, run this in Supabase SQL Editor: `delete from recommendations where rec_date < '2026-05-27';`"*. This is a literal database-admin command placed in front of the app's single non-technical user, in a decision-history table whose whole purpose is auditability — running it would permanently delete recommendation history. It also hardcodes a point-in-time date that will look increasingly arbitrary and stale as time passes, and references an internal "fixed today" cutover that only made sense on the day it was written.
- **Recommendation**: Remove the SQL snippet and the "commit"/"old verdict logic" internal framing entirely. If sparse early rows are cosmetically annoying, either filter them out of the default view in code (they're already distinguishable via NaN composite + Unverified verdict per the same expander's own text) or leave the explanation as "early rows before verdict logic matured may look sparse — this is expected and doesn't need action," with no runnable command.

### C2 — Sector/position "overweight" trim thresholds are duplicated and inconsistent across three modules ✅
> **Fixed** — commit b2e347c · 2026-07-15. Added `SINGLE_NAME_TRIM_TRIGGER=18.0` and `SECTOR_REDUCE_TRIGGER=20.0` to `constants.py`; wired `portfolio.py` and `earnings_advisor.py` to import them. Values unchanged — now have a single named source.

- **Location**: [stock_analyzer/portfolio.py:1016-1018](stock_analyzer/portfolio.py#L1016-L1018) (`diversification_recommendations`, bare `pct > 20` / `target_pct = 15.0`) and [stock_analyzer/portfolio.py:519-527](stock_analyzer/portfolio.py#L519-L527) (`rebalance_actions`, bare `w > 18` trimming to 15%) vs. [stock_analyzer/earnings_advisor.py:181-182](stock_analyzer/earnings_advisor.py#L181-L182) (bare `weight > 18` trimming to `15.0`) vs. the actual policy constants `SECTOR_CEILING`/`SECTOR_ELEVATED`/`SINGLE_NAME_CEILING` in `stock_analyzer/constants.py` that `risk_advisor.py` and `daily_briefing.py` correctly import, and `EARNINGS_OVERWEIGHT_TRIM_PCT=12.0`/`EARNINGS_OVERWEIGHT_TRIM_TO_PCT=10.0` that `daily_briefing.py`'s own earnings-overweight review item uses (daily_briefing.py:1708-1718).
- **Problem**: This is a direct violation of CLAUDE.md's hard rule #1 ("Never hardcode decision thresholds — every gate/threshold/boundary value lives in constants.py"). Three different modules answer "is this position/sector overweight, and what should I trim it to?" with three different bare-literal answers (18%→15%, 20%→15%, 18%→15% via a *different* concept than 12%→10%) instead of one shared, named policy value. A user could see a "trim to 15%" recommendation from `portfolio.py` and a "trim to 10%" recommendation from `daily_briefing.py`'s earnings module for the same overweight position on the same day, with no way to tell which one the app actually intends.
- **Recommendation**: Pick a single source of truth per axis (sector overweight vs. single-name overweight vs. earnings-specific overweight) in `constants.py`, and have all three modules import from it. This is a policy decision, not a mechanical fix — flag to the user before changing any of the three numbers.

### C3 — `earnings_advisor.py` reintroduces a magic number that was deliberately removed elsewhere for the same reason ✅
> **Fixed** — commit b2e347c · 2026-07-15. `score >= 68` replaced with `score >= COMPOSITE_STRONG_BUY` (75). User confirmed COMPOSITE_STRONG_BUY as the correct boundary for this add-before-earnings context.

The exact same un-sourced "68" boundary is alive today in `earnings_advisor.py`, a sibling module answering a structurally similar question ("is this position high-conviction enough to add to"). ### C6 — Bulk trade deletion has no confirmation step, despite being an irreversible rewrite of realized P&L history ✅
> **Fixed** — commit b2e347c · 2026-07-15. Delete button is now a two-step confirm: first click stores pending IDs in session_state and reruns; second run shows "⚠️ Permanently delete N trades?" with "Yes, delete / Cancel" buttons.

- **Location**: [app.py:16965-16980](../../app.py#L16965-L16980) ("🗑️ Delete N selected trade(s)" button) vs. [app.py:15521-15594](../../app.py#L15521-L15594) (the SELL-confirmation card on the very same page: "⚠️ Confirm this SELL before it's recorded" with explicit Confirm/Cancel buttons).
- **Problem**: Selecting rows via checkbox and clicking the delete button permanently removes trade rows and triggers a full recalculation of realized P&L across the entire trade history, with no "are you sure?" step. The same page demonstrates the app *does* have a good confirmation pattern for a comparably risky action (SELL), making the missing confirmation here an inconsistency as well as a real data-loss risk (an accidental double-click or a misread checkbox state permanently alters trade history).
- **Recommendation**: Gate the delete button behind the same confirm/cancel pattern used for SELL, or at minimum a `st.button` → `session_state` two-step ("Delete N trades?" → "Yes, delete").

### C7 — One checkbox silently disables three unrelated data-safety guards ✅
> **Fixed** — commit b2e347c · 2026-07-15. Split into three independent checkboxes: `_tj_override_price` (price sanity), `_tj_override_ticker` (ticker resolution), `_tj_override_sell` (SELL-without-holding). Each guard reads only its own key.

- **Location**: [app.py:15663-15676](../../app.py#L15663-L15676) — `st.checkbox("⚠ Allow unusual price / unrecognized ticker / SELL without holding (skip sanity checks)")`.
- **Problem**: Three independent validations — price-typo sanity, ticker-recognition, and SELL-without-a-matching-holding — are all gated by a single checkbox. A user trying to log a legitimate edge case for just one of the three (e.g., backfilling a delisted ticker the app doesn't recognize) unknowingly disables the price-typo guard and the unmatched-SELL guard at the same time, with no visibility into what else got turned off.
- **Recommendation**: Split into three independent checkboxes (or a multiselect of which checks to skip), each labeled with the specific guard it disables.

### C8 — Sidebar nav badge silently drops the warning count when a danger count is also present ✅
> **Fixed** — commit b2e347c · 2026-07-15. Badge now builds both parts independently and joins them; shows "🔴 N  🟡 M" when both are nonzero.

- **Location**: [app.py:1524-1527](../../app.py#L1524-L1527):
  ```python
  elif _dest == "⚠️ Alerts & Actions" and _n_danger_nav > 0:
      _btn_label = f"Alerts & Actions  🔴 {_n_danger_nav}"
  elif _dest == "⚠️ Alerts & Actions" and _n_warning_nav > 0:
      _btn_label = f"Alerts & Actions  🟡 {_n_warning_nav}"
  ```
- **Problem**: The two conditions are chained as `elif`, so whenever `_n_danger_nav > 0` the warning branch never evaluates — the nav badge shows only "🔴 N" even if there are also M warning-level items pending. This is the one UI element whose entire job is "tell the user something needs attention at a glance," and it's losing information exactly when there's the most to show (both danger and warning items present simultaneously).
- **Recommendation**: `_btn_label = f"Alerts & Actions  {'🔴 ' + str(_n_danger_nav) + '  ' if _n_danger_nav > 0 else ''}{'🟡 ' + str(_n_warning_nav) if _n_warning_nav > 0 else ''}".strip()`, or similar — show both counts when both are nonzero.

### I1 — Two different 4-term action vocabularies on the same page's two tabs 🔄
