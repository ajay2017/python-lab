## 1. Executive summary

Full-codebase sweep, the first since 2026-07-29 (30 commits and the entire 5-phase Judge build + F-228 Pre-Mortem enforcement have shipped since). Overall health is good — the codebase is unusually disciplined for its size (constants-driven gates, an explicit None-vs-`[]`/`{}` offline convention, visible suppression banners, real cross-feature coordination). But this sweep found **1 Critical bug that breaks a stated invariant of the just-shipped F-228 feature**, and a recurring pattern of the offline-sentinel convention being enforced correctly at the *write* end but silently defeated at several *read* ends.

**Top 3 risks:**
1. Pre-Mortem monitoring (F-228) can fire on the same day as the original BUY — the one behavior its own docstring and CLAUDE.md explicitly rule out — due to an inclusive date comparison.
2. The "producer sets `None` on failure" contract is undermined by `st.session_state.get(key) or []` at several consumer sites, silently turning "couldn't compute" into "checked, no risk" for risk alerts and diversification recs.
3. The Valuation pillar (30% of composite) fabricates a neutral 50 when no data is available — the exact failure class already fixed once for Business Quality — and its consumer (Watchlist Advisor) doesn't check availability before issuing REMOVE/ENTER_NOW calls.

**Recommended next action:** fix the Critical finding today (one-character change), then work the High list — most are narrow, well-isolated fixes (add a constant, add an availability check, fix a missing cache assignment) rather than redesigns.

This was a FULL sweep — the entire codebase was in scope. Test baseline was refreshed in the same session (3120 passed, 74% coverage — see `docs/test-results.md`).

## 2. Critical issues

**`stock_analyzer/premortem_monitor.py:226`** — Pre-Mortem trigger detection can fire on the same day as the BUY, violating its own documented "never fires same-day (close-basis)" invariant (also stated in CLAUDE.md's memory index for F-228).
```python
closes = closes[closes.index.date >= governing["buy_date"]]
```
The `>=` includes the BUY date's own close in the breach-scan window. If a user's BUY-day close already crosses the stated trigger price (a real scenario for a volatile name, or simply if `hist`'s "today" bar reflects an intraday quote rather than a settled EOD close on days the market is still open), `first_breach_date` resolves to `governing["buy_date"]` itself and `days_since = 0` — the Act Today card fires "It happened on `<today>` — 0 day(s) ago" on the purchase day itself.
**Why it matters:** this is the one behavior the feature was explicitly designed never to do (a same-day fire would just be re-stating the user's own entry price back at them, not a forward signal). It undermines trust in the very first Act Today cycle a new commitment could ever go through.
**Fix:** change `>=` to `>` at line 226.

## 3. High-priority issues

1. **`stock_analyzer/valuation.py:106`** — `score = round((points / max_points) * 100, 1) if max_points > 0 else 50.0` fabricates a neutral 50 when forward P/E, FCF yield, and analyst target/consensus are all unavailable, with no `val_available`/similar flag exposed — unlike the parallel, already-fixed Business Quality gate (`fundamentals_available` in `bundle_loader.py:222`, driving app.py's "🚫 Verdict withheld" UI at e.g. lines 16915-16920). **`stock_analyzer/watchlist_advisor.py:188-252`** compounds this: it reads `data.get("total")` (which blends the fabricated 50 in at 30% weight) with no availability check at all before issuing REMOVE (`score < 44`) or ENTER_NOW (`score >= COMPOSITE_BUY`) — a real-money buy/remove call built partly on a data-outage artifact.
   **Fix:** add a `val_available` flag from `valuation_score` (e.g. `max_points > 0`), thread it into `bundle_loader.load_bundle` alongside `fundamentals_available`, and check both in `watchlist_advisor.py` before a REMOVE/ENTER_NOW verdict.

2. **`stock_analyzer/risk.py:239-260`** (`compute_portfolio_risk_metrics`) returns `{}` — not `None` — on 4 separate insufficient-data guards, despite its own docstring calling this "insufficient data" not "zero risk." Traced downstream: `risk_advisor.py:93-94` treats `{}` and `None` identically → `[]`; and in `app.py`, consumers read the resulting cache with the idiom `st.session_state.get("_risk_advisor_recs_cache") or []` (lines 9729, 10523, 12656) and `st.session_state.get("_div_recs_cache") or []` (line 9729) — collapsing "couldn't compute" into "confirmed no risk / no gaps" with no offline banner. Watchlist's own offline check (`app.py:18680`) only tests `is None`, so it misses this path entirely.
   **Concrete failure:** a held ticker with <10 days of overlapping price history (e.g. right after a provider blip or a freshly re-added holding) silently empties every downstream risk alert and diversification-gap surface, letting an `ENTER_NOW` recommendation through un-gated.
   **Fix:** return `None` from `compute_portfolio_risk_metrics`'s insufficient-data branches (matching its own docstring's intent), and/or have every consumer read with `.get(key)` + an explicit `is None` check rather than `or []`.

3. **`stock_analyzer/portfolio.py:80-85`** — the profit-lock ratchet stop ladder (`_RATCHET_LEVELS`, 4 gain-trigger/floor-lock pairs) is a hardcoded module-level list, not in `constants.py`, despite driving the single most consequential protective-stop mechanism in the app (`protective_stop()`, `stop_ladder()`). Direct Hard Rule #1 violation, invisible to `scripts/check_constants_documented.py` because that script only audits `constants.py`'s own contents.
   **Fix:** move to `constants.py` as `STOP_RATCHET_LEVELS`, import into `portfolio.py`.

4. **`stock_analyzer/db.py:594-601`** — the read-only-viewer security backstop (`_READONLY`/`set_readonly()`/`is_readonly()`) is a plain module-level global, not `st.session_state`-scoped, but is set at the top of every script rerun (`app.py:2023`) based on that session's own viewer identity. Streamlit runs each browser session's script in its own thread within the same process, so this global is shared across concurrent sessions. A read-only viewer's session setting `_READONLY=True` can be raced by the owner's own concurrent rerun setting it back to `False` before the viewer's write call executes, letting a non-owner write succeed (or, in reverse, spuriously blocking a legitimate owner write).
   **Fix:** don't gate writes on a process-global; resolve/pass the caller's readonly flag explicitly into each writer, or at minimum store it in `st.session_state`.

5. **`app.py:19555` vs `19713-19714` vs `20222-20227`** — the Trade Journal double-submit guard is non-functional for SELL, the exact trade type its own comment cites as the original incident ("two COIN SELLs of 5 within the same second"). The BUY success path sets both `_tj_last_submit_sig` and `_tj_last_submit_ts`; the SELL success path (line 19555) sets only the signature — `_tj_last_submit_ts` is written exactly once in the whole file, on the BUY branch. The guard's 15-second window check (`(time.time() - _last_ts) < 15`) at submission time therefore always sees a stale/zero `_last_ts` after a SELL, so a resubmitted duplicate SELL within 15s is never caught.
   **Fix:** set `st.session_state["_tj_last_submit_ts"] = time.time()` alongside `_tj_last_submit_sig` on the SELL success path too (mirroring line 19714).

6. **`app.py:20074-20091, 20420, 19603`** — the required Pre-Mortem "what would make me wrong" commitment box (`_tj_premortem_commitment`) isn't ticker-scoped: it's a static-keyed `st.text_area` with no reset tied to a ticker change, and the hard gate at submission only checks non-emptiness. It's cleared **only** on a successful BUY save. A user who writes a commitment for ticker A, gets blocked by an unrelated gate (price sanity, R:R), then switches to ticker B without touching the box, can submit B's BUY with A's stale, ticker-mismatched commitment — which also seeds a bogus trigger price/direction into the F-228 forward monitor for the wrong company.
   **Fix:** clear/invalidate `_tj_premortem_commitment` whenever the resolved ticker changes, mirroring the existing `_pm_case_stale = _pm_case_for != _pm_tk` pattern already used for the AI case-against box on the same page (line 19985).

7. **`stock_analyzer/providers/finnhub_provider.py:77-80,124-126`** — unlike `fmp_provider.py`'s blanket `_safe()` key-redaction, Finnhub logs `str(exc)[:100]` raw into `api_health`. `providers/_util.py:55-70`'s URL redaction only covers the `requests.HTTPError` branch; a `ConnectionError`/`Timeout` raised by `requests.get()` itself propagates with the full `?token=<KEY>` URL intact into the Data Health tab, visible to any viewer including a read-only one.
   **Fix:** move key redaction into `_util.http_get_json` itself (wrap the `requests.get()` call, not just the `raise_for_status()` branch) so every provider gets it for free.

8. **`app.py:4301` vs `stock_analyzer/headless_alert_engine.py:340,412`** — the bull/bear market-tone threshold (`±0.5%` on S&P daily move) is hardcoded identically in both the interactive app and the headless cron path, with no shared constant, and it directly selects `COMPOSITE_BUY` vs. `COMPOSITE_BUY_FLAT_DAY` in the cron path (line 412). A future tuning of this cutoff in one path silently desyncs the cron's emailed morning picks from Grow Today's live gate the same day.
   **Fix:** add `MARKET_TONE_BULL_PCT`/`MARKET_TONE_BEAR_PCT` to `constants.py`, import in both files.

9. **`stock_analyzer/news_intelligence.py:119`** — hardcodes `-0.25` (a duplicate-drift copy of `NEWS_SENTIMENT_CRITICAL` at `constants.py:618`) plus two ungoverned cutoffs (`weight >= 8.0`, `tier <= 2`) for the critical/warning news-alert split. A future retune of `NEWS_SENTIMENT_CRITICAL` silently stops matching this classifier.
   **Fix:** import `NEWS_SENTIMENT_CRITICAL`; add named constants for the weight/tier cutoffs.

- `manual_stop_wins()` (`portfolio.py`) as the single shared predicate across `build_portfolio_df`/`stop_ladder`/Analysis's manual-stop merge — engineered to prevent the exact split-brain drift that caused a real prior incident.
- The explicit None-vs-`[]`/`{}` "offline vs. checked-empty" convention, documented in-code and correctly implemented at nearly every *producer* site checked (`exit_advisor.py`, `structural_scanner.py`, `catalyst_stress.py`, `risk_advisor.py`'s `_beta_ok`/`_f` split, Home's cache-publish block) — the gap found in this audit is specifically at several *consumer* read sites, not the producers.
- `decision_bucket.py`'s canonical `_ticker()` resolver, used consistently by every dedup-sensitive function in the file — no drift found across macro/PROTECTIVE_TRIM's differently-shaped records.
- The Judge's Phase 4 coherence audit is genuinely audit-only end-to-end — confirmed no override/suppression path exists anywhere in `app.py`'s Judge page render.
- Provider capability-declaration + failover (`providers/base.py`/`orchestrator.py`) cleanly separates "not configured" / "no data" / "unusable data," and `prev_close` is never fabricated as `prev==price` across all three providers (a previously-fixed bug that hasn't regressed).
- Supabase access is exclusively via the parameterized query builder everywhere in scope — no SQL-injection surface found anywhere in `db.py` or its callers.
- `broker_import.py`/`broker_screenshot.py` are pure parsers with a human-preview step before any DB write — no `eval`/`exec`, typed coercion with explicit invalid-row buckets rather than silent drops.
- Per-ticker failure isolation in every cron batch loop checked (`headless_alert_engine.py`, `earnings_intel.py`, `intraday_entry.py`, `stress_test.py`) — one bad ticker never aborts the run.
- `nav_page`/`_pending_page` indirection is fully consistent — 37 grepped write sites in app.py's first 9000 lines, zero direct `nav_page=` assignments outside the one sanctioned consumption block.
- SELL-exceeding-held-shares is double-checked against the trade-history replay, not just `holdings_df` — closes a real prior drift class rather than reintroducing it.
- Account page's equity/leverage separation is implemented correctly: gates run strictly on equity; `_leverage_cache` is read-only and never found gating anything.
- `constants.py`'s density of rationale comments (why each threshold, what incident/audit named it) is a genuinely strong audit trail, rare at this codebase size.

## 7. Systemic observations

1. **The offline-sentinel contract is enforced at the write end but not mechanically checked at the read end.** Three independent review passes (advisors, data-layer, app.py-Judge/Scanner) each separately found the same defect class: a producer correctly returns/caches `None` on failure, but a downstream consumer reads it with `st.session_state.get(key) or []`/`or {}`, silently re-collapsing "couldn't compute" into "confirmed empty." This is the single most repeated finding in this audit — worth a shared helper (e.g. a `get_or_offline(key)` that raises/flags rather than silently defaulting) instead of trusting every future read site to remember the `is None` check by hand.
2. **Hard Rule #1 ("every threshold lives in constants.py") is honored in the newest, most carefully-built modules (Judge, Pre-Mortem, the core scoring formulas) but has drifted in a long tail of older/adjacent modules** — and `scripts/check_constants_documented.py`'s mechanical CI gate cannot catch this, since it only audits `constants.py`'s own contents, not the absence of a threshold that was never added there. The "mechanically enforced" claim in CLAUDE.md's Definition of Done step 1 covers documentation of existing constants, not detection of missing ones.
3. **A fabricated-neutral-50-on-no-data pattern was fixed once (Business Quality, the documented PINS/HUBS incident) but survives unfixed in the sibling Valuation pillar**, and its consumer doesn't check either pillar's availability flag — an instance of "fixing the instance, not the class," which is the exact regression mode CLAUDE.md's own audit methodology (Step 2.5) warns about for a *different* prior incident (the `unsafe_allow_html` XSS class).
4. **Decision-relevant thresholds get duplicated verbatim across the interactive `app.py` path and the headless `cron_runner.py`/`headless_alert_engine.py` path** (market tone, in this audit) rather than sharing one constant — a structural risk specific to this app's two-runtime architecture that wouldn't exist in a single-runtime app.
5. **Same-day-fire / off-by-one date-boundary bugs recur across unrelated modules** (`premortem_monitor.py`'s inclusive `>=`, `portfolio.py`'s naive `date.today()`, `trade_analytics.py`'s naive `utcnow()`) — a shared, tested NY-timezone "trading-day arithmetic" helper (the app already has the pieces, e.g. in `data.py`) consistently reused would close this whole class at once rather than one date-math bug at a time.
