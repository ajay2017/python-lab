## 4. High-priority issues

**1. ⚙️ App Settings: editing a second reference table mid-edit silently orphans unsaved changes in the first, which can resurface as stale grid state later — on the exact tables that feed the macro-suppression gate.**
`app.py:31234-31251` (Edit-button disable logic) + `app.py:31305-31317` (`st.data_editor` keyed per-table).

Verified directly against HEAD: the per-table "Edit" button is only `disabled` when `_as_edit_table == _as_key` (`app.py:31248`) — i.e. it disables re-clicking the table *currently* being edited, but does nothing to the other two tables' buttons. Clicking "Edit" on table B while table A has unsaved `st.data_editor` edits immediately reassigns `st.session_state["_as_edit_table"] = "B"` and reruns, with no confirmation and no pop of table A's widget key (`f"_as_editor_widget_{_as_edit_table}"`, `app.py:31317`) — only the `Discard`/`Save` buttons pop that key (`app.py:31358-31361`, `31400-31402`), and neither runs on a table switch.

Consequence: `st.data_editor` is keyed per-table (`_as_editor_widget_sector_universe`, `_as_editor_widget_discovery_universe`, etc.), and Streamlit's documented keyed-widget behavior is to ignore a newly-passed `data` argument once session_state already holds that key's value (the same class this repo already tracks in memory `feedback_streamlit_widget_options_state.md`). So: edit table A, switch to table B without discarding/saving, later click "Edit" on table A again — the grid shown is the **abandoned, unsaved edit from earlier**, not a fresh `reference_data.resolve_universe("sector_universe")` read, while the caption directly above it (`app.py:31294-31298`) still shows the freshly-resolved "as of" date as if the grid matched it. A subsequent Save on table A would then commit that stale/abandoned payload — a silent partial revert of a roster (`sector_universe` / `discovery_universe` / `sector_candidates`) feeding exactly the macro-suppression gate this window's five discovery-bucket fixes (`6a7ef61`, `934413d`, `ddc7697`, `3cb77b7`, `3b34cb5`) were closing.

**Fix:** disable all three Edit buttons whenever `_as_edit_table` is truthy (`disabled=bool(_as_edit_table)`), not just the matching one — cheapest, one-line change at `app.py:31248`. Alternative: pop `f"_as_editor_widget_{_as_edit_table}"` (and its `_as_confirm_*` sibling) whenever `_as_edit_table` changes to a *different* table, so switching away always discards.

## 8. Systemic observations

- **The antipattern baseline can admit brand-new debt as easily as pre-existing debt, and nothing distinguishes the two cases.** `portfolio_health.py`'s naive-date bug (Medium, §5) was baselined at the time its file was created (July), not discovered later — the ratchet's "only new instances fail" design assumes baseline entries represent debt that predates the gate, but a commit can add a violation and its own baseline exemption in the same diff, and the gate has no way to tell those apart from genuine legacy debt. Worth a lightweight convention (e.g. a comment requirement, or dating baseline entries) if this recurs.
- **Doc drift can hit CLAUDE.md's own body, not just per-feature docs.** The Gate Suppression Ledger finding (§5) is the same class CLAUDE.md's Definition-of-Done step 7 was written to prevent for plan docs — it just happened to CLAUDE.md's own queue text instead, on the same day the fix shipped, and was caught only because MEMORY.md (a different, better-synced file) said something different. CLAUDE.md is loaded into every session unconditionally; a divergence there has a longer blast radius than a stale plan doc.
- **The App Settings finding and the `validate_payload` gap are the same underlying risk wearing two hats: the roster tables that gate macro-suppression have exactly one enforcement layer (a single `app.py` call site), and that layer has known holes on both the read side (coverage) and the write side (widget staleness).** Given this window spent five separate commits closing macro-gate holes on discovery-mover tickers, it's worth treating the editor that can reopen those same holes as part of the same body of work, not a separate concern.
