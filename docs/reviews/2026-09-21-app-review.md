## Verdict

The app's outcome-measurement discipline is real but sharply uneven: the three newest recommendation types (`rebal_trim`/`beta_trim`/`diversify_add`) get full capture-and-grade treatment, while six older, larger, dollar-quantified `risk_advisor` calls plus RISK_OFF trims get none at all — the single highest-value gap found. Two genuine defects turned up outside the measurement question: a live coordination bug on the Analysis page that can silently hide an active Reduce/Exit call, and a cron reliability gap where a lane's heartbeat reports "ok" even when its individual data writes fail. Newly-built, correctly-engineered features (Portfolio Investigator, 📄 Reports, the protective-track-record disclosure) are held back by real reach friction, not logic bugs — buried placement, no cross-links, narrow trigger conditions. Documentation is unusually solid at the constants level (35/35 spot-checked clean) but `docs/architecture.md` has two confirmed stale module-intro claims. Nothing here rises to "needs a new subsystem" — the highest-leverage move is extending a pattern the app has already proven works, not inventing a new one.

## Part 1 — What's working

**Closed-loop decision surfaces (decide → capture → measure → feed back), verified in code:**
- **BUY / ENTER_NOW** — decided in `daily_briefing.py`/`watchlist_advisor.py`, captured into `recommendations`, measured by `recommendations_history.py` (action rate, alpha vs SPY), rendered on 📜 Recommendations History and the Engine Track Record Offense facet. ENTER_NOW joined this pipeline 2026-09-09 (F-264).
- **EXIT/TRIM (protective)** — decided in `exit_advisor.py` (WATCH/TRIM/EXIT tiers, `exit_advisor.py:64-66`), measured by `protective_track_record.py:18-45` (sign-flipped alpha vs SPY), rendered as Engine Track Record's Defense facet. This pipeline already produced a real verdict (A1: `protect_alpha` measured negative — see CLAUDE.md's Investor Maturity Roadmap entry).
- **`rebal_trim` / `beta_trim` / `diversify_add`** — decided in `rebalancer.py` + `risk_advisor.py`'s beta card (via `beta_repair.py`), captured by `rec_events_capture.py:79-334`, measured by `rec_events_readout.py:26-41`, rendered on 🎯 Recommendation Outcomes.
- **Gate suppressions (13 gate IDs)** — decided at each site in `gate_registry.py:17-32`, captured by `gate_ledger.py`, measured by `gate_ledger_readout.py:26-48`, rendered on 🛑 The Road Not Taken.
- **Self-initiated buys/sells vs. engine** — `self_track_record.py` independently re-derives every trade's true origin and grades both sides against `recommendations_history`/`exit_signals`, rendered on 🎯 My Edge.

**Architecture that is genuinely load-bearing, not just tidy:**
- The `constants.py`-as-policy discipline is real, not aspirational — 35 constants spot-checked directly against `docs/architecture.md`'s constants table and CLAUDE.md's inline mentions came back **100% accurate**. For a project this size and age, that is a rare result and worth protecting.
- `_notify_failure` firing *before* `_record_heartbeat` in the cron dispatcher (`cron_runner.py:2700-2705`) — a real, deliberate ordering decision so a DB outage can't delay the dead-man's-switch email behind a connection timeout. This is genuine engineering, not ceremony.
- The publish/consume `st.session_state` coordination pattern mostly works as documented — two confirmed-correct sites (`app.py:41148`, `42790`) route through the documented None-safe `suppress_orphans_under_reduce_call()` helper exactly as CLAUDE.md describes. (One confirmed miss elsewhere — see Defects.)
- The Investigator's closed-toolbox design (`stock_analyzer/investigator.py`) — a fixed, code-validated function registry with a required refusal-eval gate before any model is offered — is real defense against LLM hallucination, not a paper policy.

**What to keep untouched if the app had to be cut in half:** the `constants.py` policy-threshold discipline, the deterministic pytest/antipattern/constants-doc commit gates, and the closed-toolbox pattern behind the Investigator. All three are cheap, load-bearing, and nothing else in the app substitutes for them.

## Part 2 — Next nice-to-haves (ranked, value ÷ blast radius)

### 1. Extend outcome capture to the six unmeasured `risk_advisor` recommendation types
**What:** `rec_events_capture.py:14-28` captures exactly three `rec_type`s (`rebal_trim`, `beta_trim`, `diversify_add`). Six other `risk_advisor.py` recommendation types are real, dollar-quantified, named-ticker actionable calls with **zero** outcome tracking anywhere: `sharpe` (`risk_advisor.py:445-480`, trim 40-50% on named tickers), `sector_concentration` (`:828-881`, dollar-quantified sector trim), `single_name_concentration` (`:896-931`, named-ticker dollar trim), `volatility` (`:525-540`, cash-buffer sizing), `drawdown` (`:591-627`, ATR-multiplier tightening advice), `tail_risk` (`:651-690`, CVaR-narrowing add/buffer). Plus RISK_OFF trims (`exit_advisor.py:545-650`), which `protective_track_record.py:18-20,44` explicitly and deliberately excludes as "portfolio-wide, not per-ticker" — but the action itself names specific tickers and trim percentages, so that exclusion leaves a real per-ticker decision permanently unmeasured.
**Why it matters:** this is the exact same shape of decision that `rebal_trim`/`beta_trim`/`diversify_add` already prove out — the app is already willing to measure a trim recommendation's real-world outcome. These six (plus RISK_OFF) are simply outside that net for no principled reason found in code or CLAUDE.md.
**What it touches:** `rec_events_capture.py` (new builder functions, following the existing 3-type pattern exactly), `rec_events_readout.py` (extend the grading), no schema change needed if `rec_events`' existing columns generalize (verify at build time).
**Rough cost:** moderate — a `planner` pass to confirm each type's "predicted metric" and "acted" definition (mirroring the `rebal_trim`/`beta_trim` precedent), an `implementer` build, mandatory `reviewer` (touches `_GATE_FILES`).
**What breaks if wrong:** a mis-attributed outcome could make a rec type look better/worse than it is — mitigated by copying the existing, already-reviewed capture pattern's safeguards (10-day action window, exact-ticker match, portfolio-level-proxy framing) rather than inventing new logic.

## Part 3 — Innovations

Constrained to: single user, no team, Railway Hobby + Supabase, real LLM budget, and the owner will not accept anything that manufactures a buy signal or loosens a protective gate. I considered four candidates and rejected two before presenting: an automated cron-driven reconciliation of the Investor Maturity Roadmap's manual diagnostic scripts (rejected — those scripts appear to deliberately require the owner's own Supabase credentials, and I could not verify in code whether that's an access-boundary decision or just an oversight; proposing to automate a boundary I don't understand risks proposing to remove a deliberate control), and a unified "Book Health Score" combining the existing Book Safety/Portfolio Health/Risk Posture zones into one number (rejected — the information already exists on 🧾 Summary in a more granular, more honest form; compressing it into one score adds narration risk without adding information, and risks reading as the app "deciding" more than it already does).

### A. A single coordination-context helper, used everywhere a page currently reads raw `session_state` for the same ticker facts
**Thesis:** the Analysis-page bug found in this review (`app.py:22922`) isn't really a one-off typo — it's the coordination pattern's structural risk made concrete: every page that needs "is this ticker under a reduce call / leveraged / gate-flagged" re-implements its own read of the same 3-4 caches, and CLAUDE.md's own coordination-pattern section already lists ~25 such caches. A new pure function, e.g. `stock_analyzer/coordination.py::ticker_context(ticker, session_state)`, returning an explicit tri-state dict (`{reduce_call: dict|None|"not_checked", leverage_note: ..., ...}`) would let every page call ONE audited function instead of each re-deriving the same `or {}`-shaped risk independently.
**Smallest honest version:** build it for exactly the two caches involved in the bug just found (`_reduce_calls`, `_leverage_cache`), wire it into the Analysis page only (replacing the existing ad-hoc read), leave every other page's existing reads alone for now.
**Falsifiable signal:** if, six months from now, the SAME sentinel-collapse bug class shows up on a *different* page that didn't use this helper, the innovation didn't solve the coordination problem — it just relocated the risk into a nicer-looking module. That would mean the real fix is a mechanical antipattern-gate rule (name-check the specific documented caches), not a shared library nobody is forced to use.

### B. Fold the standing ledger verdicts into the existing Weekly Debrief email, instead of requiring page visits
**Thesis:** the app has built real measurement (Engine Track Record, Gate Suppression Ledger, Recommendation Outcomes, Self Track Record) but consuming it today means actively remembering to visit 3-4 separate owner-only pages. The Weekly Debrief email (`notify.py`, already shipped, already weekly-cadence) is the one surface that reaches the owner without them having to go looking. A new section — "this week's ledger movement" — could state, in plain sentences, which gate/rec_type crossed into an evaluable verdict this week and what it said, reusing the existing readout functions verbatim (no new computation).
**Smallest honest version:** one new paragraph in the existing email, populated only on a week where at least one ledger's `band` actually changed state (never fabricate "nothing changed" as content — silence is correct when nothing moved).
**Falsifiable signal:** after two months, ask directly whether this changed anything the owner actually reads/acts on, or whether the owner still checks the pages manually regardless. If the email section goes unread while the manual page visits continue, the friction wasn't in "where do I find this" — it was somewhere else, and the digest should be retired rather than kept as unread noise.

## Defects flagged

1. **`app.py:22922` (Analysis page) — real coordination bug, `_reduce_calls` sentinel collapse.** `(st.session_state.get("_reduce_calls") or {}).get(str(ticker).upper())` collapses a not-yet-published `None` into an empty dict. If Home has run (`_port_df_enriched` ready) but the Daily Brief hasn't yet published `_reduce_calls` this session, a ticker genuinely under an active EXIT/TRIM/Reduce call gets silently treated as clean for add-sizing purposes — no warning banner fires, because the banner's own gate (`_sa_port_state != "ready"`, `app.py:22571`, keyed off `_port_df_enriched` only) doesn't check `_reduce_calls`'s own readiness. An identical-shaped occurrence exists at `app.py:22769`. The correct pattern already exists in the same file at `app.py:41148`/`42790` (an explicit `_coord_cache_state("_reduce_calls") == "ready"` check feeding the documented None-safe `suppress_orphans_under_reduce_call()`), confirming this is a local miss, not a design constraint. **Verified directly by the lead, not just the research pass.**
2. **`cron_runner.py`'s `_run_eod` (and likely its sibling lanes, same dispatcher shape) reports a green heartbeat even when individual data writes silently fail.** Every secondary write inside `_run_eod` (`account_daily_snapshot`, `portfolio_risk_snapshot`, `rec_events`, `sentiment_snapshot`, `daily_regime`, `model_predictions`) is wrapped in its own try/except that only logs — never sets the function's return code. `_run_eod` returns `0` unconditionally (`cron_runner.py:753`) unless the *entire* run is blocked by a full DB outage. The dispatcher (`cron_runner.py:2715-2719`) then records `status="ok"` whenever `rc==0`. **Verified directly by the lead** (read the actual try/except blocks and the unconditional `return 0`). This is the same "form vs. substance" shape CLAUDE.md's own commit-hook caveat already names, recurring in the data pipeline instead of git history.
3. **`docs/architecture.md:2540` — stale function count for `broker_sync.py`.** States "Five functions:" and lists 5; the file actually defines **17** top-level public functions today (verified: `grep -c "^def [a-z]" stock_analyzer/broker_sync.py` → 17). Several of the missing 12 (`income_event_subtype`, `dedupe_income_events`, `parse_robinhood_csv_income`) are individually documented elsewhere in the *same* architecture.md section, so this is a stale summary line, not a substantive gap.
4. **`docs/architecture.md:2197-2198` — `gate_registry.py`'s module intro lists only 8 of the 13 live gate IDs.** `GATE_IDS` (`gate_registry.py:17-32`) genuinely has 13 entries (the original 8 plus G-02/G-05/G-06/G-13/G-18 from the 2026-09-13 B2 expansion) — **verified directly**. The same architecture.md section describes that expansion in detail 38 lines further down, so the doc contradicts itself within one section. `docs/requirements.md`'s own gate table is already correct — this drift is architecture.md-only.
5. **CLAUDE.md's `app.py` line-count justification is dated and now understates by ~14%.** States "38,197 lines... (measured 2026-08-28)"; actual current `app.py` is 43,691 lines. The date qualifier means this isn't a false claim, but the number underpins the "app.py decision logic is unverifiable" argument and has grown further since it was last measured.
6. **The new `tests/test_system_health_inventory_completeness.py` guard is single-hop, not true reachability.** It only resolves `db.save_*` calls made directly from `cron_runner.py`, and only `.table("literal")` calls written directly inside that function's body in `db.py`. A future write path that goes through an intermediate helper (two hops instead of one) would pass the guard silently while remaining genuinely invisible to System Trust — the exact class this guard was built to prevent. Not urgent (no such path exists today, verified by the research pass), but worth noting as a known limitation rather than assuming the guard is airtight.
