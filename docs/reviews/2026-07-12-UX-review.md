# DRISHTA — UX Audit
*2026-07-12 · Full app · app.py (21,061 lines), stock_analyzer/*.py*

---

## Executive Summary

DRISHTA is a dense, data-rich tool whose core decision logic is genuinely well-structured and intentional — the Brief-first hierarchy, gate explanations, and progressive disclosure via expanders all reflect careful design. The single biggest opportunity is a batch of developer-internal strings that leak directly into user-facing copy (file paths, table names, source-code symbols, Python snake_case identifiers) concentrated on five pages; these corrode the professional credibility the app otherwise projects, and several are fixable in under an hour. A secondary cluster is vocabulary inconsistency — the same concept (a recommendation the user should act on today) is labelled "alert," "signal," "action," "rec," "pick," and "directive" interchangeably, making it hard to build a mental model of what the app is telling you.

## Critical Issues (fix before launch)

### C1 — Developer-internal strings exposed to users (five pages)

- **Location**: `app.py:1441`, `app.py:14357`, `app.py:16552–16559`, `app.py:17476–17477`, `app.py:20131`, `app.py:20190`
- **Problem**: Five distinct surfaces render source-code symbols and infrastructure paths verbatim into user-visible banners. A daily retail investor has no way to action "update NYSE_HOLIDAYS in constants.py" or "DDL activated 2026-06-27." These strings break the professional persona the app projects.
  - `app.py:1441` — Sidebar caption: `"⚠️ Holiday calendar is out of date — update NYSE_HOLIDAYS in constants.py."`
  - `app.py:14357` — Trade Journal warning: `"Add your Supabase credentials in `.streamlit/secrets.toml` to persist trades permanently."`
  - `app.py:16552–16559` — Trade Journal DB setup: `"Run the SQL in `stock_analyzer/db.py` to create the `trades` table, then add your credentials to `.streamlit/secrets.toml`."` (also rendered as raw `<code>` HTML)
  - `app.py:17476–17477` — Recommendations History warning: `"Run the SQL migration in `stock_analyzer/db.py` and set credentials in `.streamlit/secrets.toml`."`
  - `app.py:20131`, `20190` — AI Insights weekly debrief warning: `"Check back after more days accumulate (DDL activated 2026-06-27)."` / `"DDL activated 2026-06-27)"`
- **Recommendation**:
  - `app.py:1441` → `"⚠️ Holiday calendar needs updating — contact your administrator."`
  - `app.py:14357` → `"Connect a database to persist trades between sessions. See the setup guide."`
  - `app.py:16552–16559` → `"A database connection is required. Run the one-time setup in the setup guide."`
  - `app.py:17476–17477` → `"A database connection is required to record and display recommendation history."`
  - `app.py:20131`, `20190` → Remove `"(DDL activated 2026-06-27)"` entirely; the preceding sentence is sufficient.

### C2 — Python snake_case identifiers surfaced as filter options (Recommendations History)

- **Location**: `app.py:17529–17530`
- **Problem**: The Rec type multiselect filter shows `new_pick`, `add_winner`, `buy_candidate` as selectable options — raw Python identifier strings. A user opening this filter for the first time sees underscored machine tokens, not human labels. This directly affects discoverability: a user curious about "Opportunity Watch" signals will not know to look for `buy_candidate`.
- **Recommendation**: Replace the multiselect options with human-readable labels:
  - `"new_pick"` → `"New Position"`
  - `"add_winner"` → `"Add to Winner"`
  - `"buy_candidate"` → `"Opportunity Watch"`
  Store the mapping in a dict so the filter still passes the internal key to the query logic.

### C3 — `pt_change` Python identifier in Analyst Coverage report type selectbox

- **Location**: `app.py:20701`
- **Problem**: The analyst report type selectbox (`_ac_rtype_opts`) lists `["initiation", "upgrade", "downgrade", "reiteration", "pt_change", "other"]`. All other options are recognisable human words; `pt_change` is a Python identifier. A user selecting a report type for a price-target change will either miss it (scanning for "Price Target") or select `"other"` incorrectly, corrupting the research data.
- **Recommendation**: Replace `"pt_change"` with `"Price Target Change"`.

### C4 — Grammar error erodes professional credibility on Watchlist caption

- **Location**: `app.py:13746`
- **Problem**: `"A Institutional PM doesn't just track watchlist tickers; they actively manage them."` — "A" before a vowel-sound word is incorrect grammar. On a page pitched at users who should trust the app's judgement, a visible grammar error undermines that confidence disproportionately.
- **Recommendation**: Change to `"An institutional PM doesn't just track watchlist tickers; they actively manage them."`

### C5 — Verdict label hardcodes `EARNINGS_IMMINENT_DAYS` and will silently drift

- **Location**: `stock_analyzer/daily_briefing.py:319`
- **Problem**: `verdict_label = "⚠️ Caution — Earnings Within 7 Days"` hardcodes the value of `EARNINGS_IMMINENT_DAYS` (currently `7`). If the constant is changed to `5` or `10` as an investment-policy decision, the label the user reads ("Within 7 Days") will contradict the actual gate logic, and the app's own User Guide will disagree with what the Brief fires on.
- **Recommendation**: Build the label from the constant: `verdict_label = f"⚠️ Caution — Earnings Within {EARNINGS_IMMINENT_DAYS} Days"`. The same pattern should be audited for the User Guide static text at `app.py:17988`.

## Improvements (high value, not blocking)

### I1 — Home page has 11 tabs — cognitive overload before the first action

- **Location**: `app.py` (Home page tabs definition, ~line 4430–4440)
- **Problem**: The Home page presents 11 tabs side by side: `📋 Today's Brief | 🌙 Evening Debrief | 📊 Overview | 📈 Performance | 💰 P&L Attribution | ⚠️ Alerts & Actions | 🔗 Risk Analysis | 📈 Relative Strength | 🔥 Sector Rotation | 🏆 Rankings | 🤖 AI Brief`. Before the user has made any decision, 11 parallel topics compete for attention. The "decides, not informs" operating posture should make Today's Brief the dominant viewport; everything else should recede.
- **Recommendation**: Promote Today's Brief to a prominent full-width top section (not a tab), then consolidate the remaining tabs into 4–5 grouped tabs: e.g., `📊 Portfolio` (Overview + Performance + P&L), `⚠️ Risk & Alerts` (Alerts + Risk Analysis + Stress), `📈 Analytics` (Relative Strength + Sector Rotation + Rankings), and `🤖 AI Brief`. This mirrors the precedent already set on 🧠 AI Insights, which restructured from vertical scroll to cadence tabs (commit `b8bc336`).

### I2 — Composite weights hardcoded in Market Scanner info box

- **Location**: `app.py` (Market Scanner caption, grep for `"Business Quality (35%), Valuation (30%)"`)
- **Problem**: The info box reads: `"…which adds Business Quality (35%), Valuation (30%), and Sentiment (10%) data to form a composite score."` These percentages are sourced from `COMPOSITE_WEIGHTS` in `constants.py` (`business_quality: 0.35, valuation: 0.30, sentiment: 0.10`). If weights are ever retuned as an investment-policy decision, this UI text will contradict the actual scoring with no compiler warning.
- **Recommendation**: Build the string from the constants: `f"…Business Quality ({int(COMPOSITE_WEIGHTS['business_quality']*100)}%), Valuation ({int(COMPOSITE_WEIGHTS['valuation']*100)}%), Sentiment ({int(COMPOSITE_WEIGHTS['sentiment']*100)}%)…"`

### I3 — Watchlist action codes partially visible to users

- **Location**: `app.py:13921–13926` (Watchlist action icon map); `app.py:13882–13883` (sort dict)
- **Problem**: `HOLD_OFF_EARNINGS`, `WAIT_CATALYST`, `WAIT_ENTRY`, `ENTER_NOW`, `NEAR_ENTRY`, `REMOVE` are defined as Python constants and appear in the sort dict and conditional logic. While the UI renders icons (✅, 🎯, ⏳, 👁️, ⚠️, 🔴) next to human card titles, these codes can leak into error messages and conditional banners. The card title format `"{ticker} — Good Setup, But Earnings in {n}d"` (from `watchlist_advisor.py:240`) is clear; the risk is the codes showing up in debug/error paths.
  - Opinion: The overall watchlist card copy quality is good. The risk is leakage in edge cases.
- **Recommendation**: Audit every `if _action == "HOLD_OFF_EARNINGS"` branch (there are 2+) to ensure no path renders the code string directly. Consider adding a display-label mapping dict alongside the icon map.

### I4 — "Visit Home first" empty state phrased differently on 4 pages

- **Location**: `app.py` — Macro page, Catalyst Watch, Account (both conditional branches), Risk Analysis tab
- **Problem**: When holdings haven't been loaded, four pages show near-identical but differently-worded messages:
  - Macro: `"Portfolio data not yet loaded — visit **Home** first to initialise your holdings, then return here."`
  - Catalyst Watch: `"Open the 🏠 Home page once this session to load your holdings…"`
  - Account (no portfolio): `"Open the 🏠 Home page once this session to load your holdings — then total account value…"`
  - Rate Sensitivity: `"Rate sensitivity unavailable — portfolio data not loaded."`
  The inconsistency ("visit Home first" vs "Open the 🏠 Home page once" vs "portfolio data not loaded") makes the app feel unfinished.
- **Recommendation**: Standardise to one phrase and one accompanying button. Suggested standard: `"Your portfolio hasn't loaded yet."` + `st.button("▶ Go to Home")`. Extract as a shared helper `_render_portfolio_not_loaded()` to ensure all four surfaces stay in sync.

### I5 — Hardcoded "45 days" in Economic Calendar (no backing constant)

- **Location**: `app.py` — Economic Calendar title caption, metrics, two `st.info` calls (4 occurrences)
- **Problem**: The Economic Calendar window is stated as "45 days" in at least four places in the UI, but there is no constant named `ECONOMIC_CALENDAR_WINDOW_DAYS` in `constants.py`. If the window ever changes, all four occurrences require a manual find-replace, and a missed one creates a contradiction.
- **Recommendation**: Add `ECONOMIC_CALENDAR_WINDOW_DAYS = 45` to `constants.py` (operational knob, not an investment threshold) and reference it in all four occurrences. Similarly, `CATALYST_WATCH_WINDOW_DAYS = 7` already exists in constants; the Catalyst Watch page uses it correctly via the constant — the Economic Calendar should follow that pattern.

### I6 — Correlation threshold (0.65) hardcoded in Risk Analysis metric help text

- **Location**: `app.py` — Risk Analysis tab, `st.metric("High-Correlation Pairs", …, help="Pairs with correlation ≥ 0.65")`
- **Problem**: The 0.65 threshold used to count "high-correlation pairs" is hardcoded both in the help text and presumably in the computation. If the threshold changes, the help text won't update. This is a minor but recurring pattern: threshold values should have a single authoritative source.
- **Recommendation**: Add `CORR_HIGH_PAIRS_THRESHOLD = 0.65` to `constants.py` and use it in both the computation and the help text string.

---

### I7 — VIX thresholds in Macro page delta labels don't use `RISK_OFF_VIX_LEVEL`

- **Location**: `app.py` — Macro page, VIX metric delta logic (grep for `>= 25` and `<= 15` near `"risk-off"` / `"risk-on"`)
- **Problem**: `RISK_OFF_VIX_LEVEL = 25.0` is defined in `constants.py`. The Macro page VIX metric delta appears to use hardcoded `25` and `15` for "risk-off" / "risk-on" labels. If `RISK_OFF_VIX_LEVEL` is changed as a policy decision, the Macro page label will contradict the actual gate with no error.
- **Recommendation**: Source both thresholds from constants: `RISK_OFF_VIX_LEVEL` (25) for the risk-off label; add `RISK_ON_VIX_LEVEL = 15` or use a named local. The risk-on threshold (15) is not currently in `constants.py` and should be added.

---

### I8 — Scorecard color threshold and scanner chart annotation hardcode `COMPOSITE_BUY`

- **Location**: `app.py` — Analysis scorecard color logic (`v >= 65`), Market Scanner chart heatmap annotation (`add_hline(y=65, …)`)
- **Problem**: `COMPOSITE_BUY = 65` is the authoritative buy threshold. At two rendering sites the value `65` is hardcoded rather than imported. If the threshold is raised or lowered as a policy decision, the visual coloring and chart annotation won't track the actual gate, creating a display lie.
- **Recommendation**: Import and use `COMPOSITE_BUY` at both sites: `v >= COMPOSITE_BUY` and `add_hline(y=COMPOSITE_BUY, annotation_text=str(COMPOSITE_BUY), …)`.

## Consistency Audit

| Inconsistency | Occurrences | Recommended Standard |
|---|---|---|
| "signal" vs "alert" vs "action" vs "recommendation" vs "pick" for the same concept (an engine output the user should act on) | Throughout app — Home Brief, Risk Analysis, Alerts & Actions tab, Recommendations History | Use **signal** for engine output (what it computed), **alert** for threshold-triggered notifications (stop breached, VIX spike), **recommendation** for actionable advice. Avoid "pick" (trading-floor slang) and "action" as a noun (ambiguous with button actions). |
| "WATCH" vs "MONITOR" | Exit advisor uses `WATCH`; Alerts & Actions tab renders `"⚠️" MONITOR`; User Guide table uses `WATCH · MONITOR` side by side | Standardise to **Watch** (noun-form, title-case) in all user-facing copy. |
| "Position" vs "holding" | Interchanged on every page (Home "holdings", Analysis "positions", Watchlist "holdings", Risk "positions") | Use **position** for anything currently owned; **holding** is informal — reserve it for casual phrases. |
| "Composite Score" vs "Conviction" vs "Score" vs "Quality score" | Overview tab ("Composite Score"), Home metric ("Avg Conviction"), Watchlist ("score"), Analysis ("Composite") | Use **Composite Score** everywhere as the canonical label; "conviction" is only appropriate in the context of high-conviction (score ≥ COMPOSITE_STRONG_BUY) framing. |
| "Today's Brief" vs "Daily Brief" vs "The Brief" | Tab label uses "Today's Brief"; module is `daily_briefing.py`; User Guide uses "Today's Brief"; some inline text says "the Brief" | **Today's Brief** is the correct user-facing name. |
| "Confirmed" vs "✅ Confirmed — All Signals Aligned" vs just showing a colored chip | Verdict label is verbose when full, used abbreviated in some contexts | Standardise: show the full verdict string in the Brief's buy-candidate cards; show icon+one-word (`✅ Confirmed`) in compact contexts (badges, tables). |
| `ENTER_NOW` vs "✅ Enter Now" vs "Ready to Enter" | Action code, metric label, and card title all say different things for the same state on Watchlist | Card title should be the canonical human label: `"Ready to Enter"`. Metric label: `"Enter Now"`. Never show the code. |
| "Trade Plan" vs "Analysis" tab label | The Trade Plan tab inside Analysis is labelled dynamically (sometimes "📊 Trade Plan", sometimes "📉 Exit Plan"); these are the same tab switching by position state | Keep the dynamic label but ensure the two variants ("Trade Plan" for non-held, "Exit Plan" for held positions in negative P&L) are documented in the User Guide for clarity. |
| Severity: HIGH / MEDIUM / LOW vs 🔴 / 🟡 / ✅ vs CRITICAL / WARNING / INFO | Risk advisor uses HIGH/MEDIUM; Alerts tab uses 🔴/🟡/ℹ️ metric labels; Data Health uses RED/YELLOW/GREEN | Adopt one three-tier system throughout: 🔴 **High** / 🟡 **Medium** / ✅ **Low**. The colored circle + title-case word is both machine-readable and human-friendly. |
